## 1. 목적과 비목적

### 1.1 목적
**사용자가 5G 우선 모드를 쓰고 있을 때**, 5G NSA가 불안정한 곳(지하철, 실내 깊은 곳, 커버리지 경계)에서 **데이터를 쓰는 중에 NR 보조 연결이 붙었다 떨어지기를 반복**하는 상황을 감지하면, 일정 시간 NR을 비허용(LTE 계열 모드)으로 두어 불필요한 모뎀 활동을 막는다. 시간이 지나면 NR을 다시 허용해 재시험한다.

> "5G를 끄는 도구"가 아니라 **"쓸 만할 때만 5G를 쓰게 하는 상위 정책 컨트롤러"**.

### 1.2 비목적 (하지 않는 것)
- **NR-only(5G 단독) 강제** — NSA에서는 LTE 앵커가 사라져 서비스가 끊긴다(보고: 약 33ms 내 서비스 불가). 🔒
- **사용자가 LTE 모드(5G 제외)를 고른 상태에서 5G를 켜는 것** — 그때는 순정 동작을 그대로 따른다. 🔒
- **설정 화면에 보이는 네트워크 모드와 실제 동작을 다르게 두는 것** — 표시와 실제는 항상 같아야 한다(§5.6.5). 🔒
- 밴드 고정, NR 추가/해제 임계값 변경, LTE/NR 데이터 분배 — 공개 경로 없음(서비스모드·모뎀 영역).
- "5G가 배터리를 더 먹는가"의 일반론 입증 — 이 도구는 **사용자 환경에서의 순이득**만 측정한다.
- iPhone 지원 — ADB 같은 제어 경로가 없음.
- 루트 전용 기능.

### 1.3 성공 기준 (Phase 2 A/B 측정으로 판정, §9)
1. 같은 경로·시간대에서 컨트롤러 ON이 OFF(사용자 기본 5G 모드) 대비 **데이터 사용 중 NR 연결 반복 횟수**를 줄인다.
2. 배터리 소모(데이터량·화면시간으로 정규화)가 **악화되지 않고**, 가능하면 개선된다.
3. 컨트롤러가 일으킨 전환 비용(패킷 손실·VoLTE 공백)의 누적이 사용자에게 표시되고 예산 안에 머문다.

구체 목표 수치는 실사용 기록 확보 후 정한다(지금 정하면 근거 없는 수치가 된다).

## 5. 시스템 구성

### 5.1 전체 구조

```
┌──────────── PC (Windows / macOS) ────────────┐
│ nrctl (CLI)                                   │
│  doctor · install · start · stop · status     │
│  pause/resume · keep-lte · restore · pull · report│
└───────────────┬──────────────────────────────┘
                │ adb (USB, 기동 시 1회 + 진단 시)
┌───────────────▼──────────── Android 폰 ─────────────────────────┐
│  nrd (데몬, shell uid, app_process로 기동, 케이블 분리 후 상주)   │
│   ├ Observer      : TelephonyRegistry 이벤트 구독 (binder)        │
│   ├ FeatureWindow : 슬라이딩 창 특징 추출                          │
│   ├ PolicyEngine  : 상태기계 + 가드 + 예산 + 백오프                │
│   ├ Actuator      : 백엔드 어댑터 (cmd phone …) + 읽기 재확인      │
│   ├ Journal       : JSONL 이벤트 로그 (/data/local/tmp/nrc/)       │
│   └ ControlBinder : 동반 앱용 binder (호출 uid 검사)                │
│                        ▲ binder (Shizuku와 같은 전달 패턴)          │
│  동반 앱 (일반 앱 uid)                                              │
│   ├ 상태 화면 · 기록 · 설정                                         │
│   ├ 빠른설정 타일: 자동 / LTE로 계속 쓰기 / 일시정지                │
│   └ 알림: 상태 변화 · 데몬 중지 · 복구 안내                          │
└────────────────────────────────────────────────────────────────────┘
```

### 5.2 왜 shell uid 데몬인가
- 전환에는 `MODIFY_PHONE_STATE`, 관측에는 `READ_PRECISE_PHONE_STATE`/`READ_PRIVILEGED_PHONE_STATE`가 필요하다. 일반 앱은 받을 수 없고 shell(adb)은 보유한다(근거 §4).
- 데몬 코드는 **동반 앱 APK 안에 포함**한다. PC가 `pm path <패키지>`로 APK 경로를 얻어 `app_process`로 데몬 클래스를 실행한다(scrcpy·Shizuku 방식). 배포물은 APK 1개 + PC 도구.
- 기동: `setsid`로 adb 세션과 분리. 레퍼런스 기기에서 약 18.8시간 생존 확인(P10).
- Phase 1(동반 앱 없음)은 PC 도구가 데몬 dex를 `/data/local/tmp/nrc/nrd.dex`로 올려 `app_process`로 실행한다. APK 포함 방식은 동반 앱을 만드는 Phase 3에 적용한다.
- 단일 인스턴스 보장: 데몬은 프로세스 수명 동안 배타 파일 잠금(`nrd.lock`)을 잡는다. 잠금을 못 얻으면 새 기동은 곧바로 끝난다(실측: 두 번째 기동 종료 코드 3). pid 파일은 잠금을 얻은 뒤에 쓰며, PC 도구가 데몬을 찾는 용도다. 쓰지 못하면 기동하지 않는다.

### 5.3 관측 계층 (Observer)

**주 경로: binder 이벤트 구독** (`ITelephonyRegistry`, callingPackage=`com.android.shell`)

| 이벤트 | 사용처 | 비고 |
|---|---|---|
| PHYSICAL_CHANNEL_CONFIG | **NR 연결 1차 신호**: NR + SecondaryServing 항목 존재 여부 | 화면 꺼짐 시 중단 가능(P8), 목록이 오래된 값일 수 있음 |
| SERVICE_STATE | nrState(원값, hidden getter), 데이터 RAT, 서비스 상태, LTE 앵커 셀 | 서비스 상태 OOS는 강한 불량 신호 |
| SIGNAL_STRENGTHS | LTE rsrp/rsrq/rssnr, NR ss-rsrp/rsrq/sinr | NR 값은 NR 측정 중일 때만 유효 |
| DATA_ACTIVITY + 트래픽 바이트(셀룰러 인터페이스 카운터) | "데이터 사용 중" 판정 | 정상 비활성 해제와 구분 |
| 통화 상태: Telecom 수준 통화 여부(**모든 SIM**) + 대상 subId의 CALL_STATE | 통화 가드 | 둘 중 하나라도 통화면 통화로 본다 |
| ALLOWED_NETWORK_TYPE_LIST | 사유(reason)별 변경 감지 | 콜백은 USER만이 아니라 (사유, 해당 사유의 마스크)를 전달 → §5.6.6 규칙 |
| DISPLAY_INFO | **기록 전용** — 판단에 사용 금지 🔒 | 사용자에게 보이는 아이콘과 비교용 |

- 대상 SIM 번호: 레퍼런스 기기의 app_process 실행에서 `SubscriptionManager` 정적 조회가 -1을 돌려줬다(관측, 원인 미확인 — 앱 컨텍스트 부재로 추정) → SIM 관리 서비스(`ISub.getDefaultDataSubId`)에 직접 묻는다.
- 단발 조회 `getServiceStateForSubscriber`는 **위치 정보 포기(renounce) 옵션을 켜고** 호출한다.
  - 레퍼런스 기기에서 옵션을 끈 호출(false/false)은 원격 NullPointerException으로 실패했다(관측, 원인 미확인).
  - 옵션을 켠 호출(true/true)은 nrState 원값을 정상적으로 읽었다(실측, research §2.4).
  - 셀 식별(앵커 키)은 구독 이벤트 쪽에서 얻는다 ❓(Phase 0 ④).
- 화면 상태: 이벤트 수신 시 `PowerManager.isInteractive`(hidden 서비스 호출)로 확인.
- 알림 등록 주체는 system_server의 TelephonyRegistry다(소스). 전화 프로세스가 재시작돼도 등록은 유지된다 → 데몬은 전화 프로세스 종료를 **기록만** 한다. 레지스트리(system_server)가 죽으면 구독이 끊기므로 기록하고 종료한다(조용히 살아 있으면 "사건 없음"으로 오독됨).
- AIDL 호환층: Android 버전·제조사별로 listen 메서드 시그니처가 다를 수 있음 → 리플렉션으로 후보 시그니처를 순서대로 시도, 모두 실패 시 **보조 경로**로 강등.

**Phase 1 구현 (2026-09-28, 레퍼런스 기기 실측)** — `daemon/src/nrc/`
- 등록: 공개 API `TelephonyManager.registerTelephonyCallback(INCLUDE_LOCATION_DATA_NONE, …)`를 shell 패키지 컨텍스트로 호출한다(내부적으로 위 레지스트리 구독). Android 12+ 공개 API라 위 AIDL 후보 순회는 아직 필요 없었다.
- `app_process`에서는 `ActivityThread.initializeMainlineModules()`를 먼저 호출해야 한다. 빼면 전화 서비스 조회가 null로 실패했다(실측: 등록 단계 NullPointerException).
- 첫 알림: 등록 후 5~17ms 안에 서비스 상태·통화·데이터 활동·신호·표시·물리채널 여섯 종류가 모두 도착했다(등록 성공 7회 기동, 화면 꺼짐·핫스팟·USB 충전 중).
- 허용 타입 알림(ALLOWED_NETWORK_TYPE_LIST): 인터페이스가 공개 SDK에 없어(@hide) 컴파일 때만 같은 이름의 선언(`daemon/stubs`)을 쓰고, 실행 때는 기기 프레임워크의 것을 쓴다. 기기에 없으면 공개 알림만 받는 관찰기로 내려간다.
  - 등록은 권한 오류 없이 성공했다. **등록 시점의 현재값은 오지 않았다**(7회 기동, 끝난 6회 합계 약 56분 동안 0건) → 현재 USER 값은 시작 시와 30초 주기로 직접 조회한다.
  - 값이 바뀔 때 알림이 오는지는 모드 변경이 있어야 확인된다 ❓(사용자가 설정에서 모드를 바꿀 때 기록으로 확인).
- 통화 상태는 대상 SIM의 알림만 기록한다. Telecom 수준(모든 SIM) 통화 여부는 Phase 2에서 추가한다. 레퍼런스 기기는 단일 SIM이다.
- 화면 상태·사용자 모드·발열 단계는 알림이 없어 30초 주기로 확인한다. 이 주기는 깨어 있을 때만 돈다(폰을 깨우지 않음).
- 셀 식별(앵커 키)은 위치 정보를 받지 않으므로 Phase 1에서는 수집하지 않는다(셀 기억은 Phase 3).

**보조 경로: 폴링** (`dumpsys telephony.registry` 파싱, nrState 마스킹으로 PCC·아이콘·신호만 사용) — 진단 모드(`nrctl observe`)와 구독 실패 시에만. 판정 정확도가 낮으므로 이 경로에서는 자동 전환을 끈다(관찰만) 🔒.

### 5.4 특징 추출 (FeatureWindow)

핵심 정의 — **활성 중 NR 끊김(active-drop)**: NR 연결 상태(PCC NR SecondaryServing 또는 nrState=CONNECTED)가 해제된 순간, 직전 `T_active` 초 안에 데이터 활동이 있었던 경우.
- 이것은 데이터가 없어 생기는 정상 해제를 **줄이기 위한 휴리스틱**이며 오분류가 가능하다. 예: 짧은 다운로드 직후 정상 해제되어도 마지막 데이터가 `T_active` 안에 있으면 active-drop으로 셀 수 있다. 실사용 기록으로 오분류율을 확인해 정의를 조정한다 🧪.

**전환 정착 구간(settle)** 🔒: 컨트롤러가 직접 마스크를 바꾼 시점(쓰기를 끝낸 시각)부터 "데이터 등록 IN_SERVICE 복귀 + 기본 데이터 연결 재수립" 확인 후 `T_settle`까지를 정착 구간으로 둔다. 사용자가 설정에서 모드를 바꾼 뒤에도 같은 구간을 둔다(§5.11, 기기 시험에서 발견).
- 이 구간의 OOS·NR 변화·IMS 해제는 **전환 비용으로만 기록**하고 품질 특징(`drops_W`, `oos_W`, `nr_dwell_med`)에는 넣지 않는다(실측: NR 켜기 직후 데이터 등록 OOS 1.22초 발생, research §2.2).
- 정착 확인이 `T_settle_max` 안에 오지 않으면 `SAFE_STOP`.

| 특징 | 정의 |
|---|---|
| `drops_W` | 최근 `W`초 창의 active-drop 횟수 |
| `nr_dwell_med` | 데이터 사용 중 NR 연결 유지 시간의 중앙값 |
| `oos_W` | 창 내 데이터 서비스 OOS 횟수 |
| `nr_active_ratio` | 데이터 사용 시간 중 NR 연결 비율(기록용) |
| `nr_sig` | NR ss-rsrp/sinr 통계(가용 시) |
| `anchor` | LTE 앵커 셀 키(EARFCN, PCI, 가용 시 CI/TAC) — 로그엔 해시로 저장 |
| `observability` | 화면 켜짐·PCC 보고 가용 여부. 불가 구간은 "관측 공백"으로 표시 |

- Phase 1 기록은 판정 결과(참/거짓)가 아니라 **원값**을 남긴다. NR 끊김마다 "마지막 데이터 활동 후 경과(ms)"와 "직전 NR 유지 시간"을 적는다. 그래서 `T_active` 등 기준값을 바꿔 같은 기록으로 다시 계산할 수 있다.
- 데이터 사용 구간: 데이터 활동 알림(방향 IN/OUT/INOUT)이 3초 넘게 멈추면 한 구간이 끝난다. 3초 이하의 멈춤은 구간 안에 포함한다. `nr_active_ratio`·재시험의 "데이터 사용 누적"은 이 구간으로 계산한다.
  - 기록은 (시작, 길이) 조각이다. 30초 주기마다 구간을 끊지 않고 지금까지를 조각으로 내보내며, 조각은 앞 조각 끝에서 바로 이어진다. PC가 이어 붙이면 원래 구간과 같다.
  - 계산은 안드로이드와 무관한 `daemon/src/nrc/UseSegments.java`에 두고 PC에서 시험한다(`bash daemon/test.sh`, 3초 이내 멈춤과 주기 기록이 겹치는 경계 포함).

### 5.5 정책 엔진 (PolicyEngine)

#### 5.5.1 상태

| 상태 | NR 허용 | 의미 |
|---|---|---|
| `OBSERVE` | 사용자 기본값 그대로(쓰기 없음) | 관찰 전용. 전환하지 않고 "전환했을 시점"만 기록. 사용자 모드가 5G 우선이지만 **제어 불가 조건**일 때 머무는 상태. 제어 불가 조건은 다섯 가지다: 관찰 전용 실행(Phase 1), 표시 동기화 경로 미확보(삼성의 S 미확보, §5.6.5), 관측 경로 강등(§5.3), 활성 SIM 2개 이상(§6), 상단바 작동 표시 불가·상실(§5.8) |
| `NR_GOOD` | 허용 | 5G 양호 |
| `NR_WATCH` | 허용 | 5G 경계 — 관찰 강화 |
| `LTE_COOLDOWN` | **비허용** | 5G 불량 — 쿨다운 |
| `NR_PROBE` | 허용 | 재시험 창 |
| `INACTIVE` | 사용자 모드 그대로(쓰기 없음) | 사용자 모드가 LTE(NR 미포함). 순정 동작 |
| `HOLD` | 현재 유지(쓰기 없음) | 가드 발동(통화·외부 제한·예산 소진·관측 공백·명령 실패) |
| `SAFE_STOP` | 되돌리기 조건(§5.6.3) 충족 시 원래 마스크로 복원 | 정착 확인 시간 초과 등 심각한 오류 시 정지 |

#### 5.5.2 전이

```
NR_GOOD ──(active-drop 1회)──▶ NR_WATCH
NR_WATCH ──(T_clear 동안 active-drop 0)──▶ NR_GOOD
NR_WATCH ──(drops_W ≥ N_drop 또는 oos_W ≥ 1 또는 nr_dwell_med < D_min[표본≥k])
          ∧ 가드 통과 ∧ 예산 있음──▶ LTE_COOLDOWN  (backoff_level 적용)
LTE_COOLDOWN ──(쿨다운 만료 ∧ 화면 켜짐 ∧ 가드 통과 ∧ 예산 있음)──▶ NR_PROBE
NR_PROBE: 정착 구간(§5.4) 종료 후에 평가 창을 연다 — 정착 구간 사건은 판정에 쓰지 않음
NR_PROBE ──(평가 창에서 데이터 사용 누적 P_active 동안 active-drop < N_probe ∧ OOS 0)──▶ NR_WATCH
NR_PROBE ──(평가 창에서 active-drop ≥ N_probe 또는 OOS)──▶ LTE_COOLDOWN (backoff_level + 1)
NR_PROBE ──(P_max 경과했는데 데이터 사용 부족: 판정 불가)──▶ NR_WATCH
NR_GOOD/NR_WATCH ──(T_stable 동안 안정)──▶ backoff_level = 0
모든 상태 ──(가드 발동)──▶ HOLD ──(해제)──▶ 이전 상태, 단 특징 창(drops_W 등)을 비우고 새로 시작
  예외 1: 외부 USER 변경·(출력 completed ∧ 재확인≠목표)는 "사용자 모드 선택"으로 본다(§5.6.6 2번). HOLD를 거치지 않는다 🔒
        새 값을 원래 모드로 채택하고 이전 상태로 돌아가지 않는다. 특징 창을 비우고 "활성화 판정"으로 간다.
  예외 2: 명령 실패로 인한 HOLD는 사용자가 재개(앱·CLI)할 때 기존 원래 모드로 "활성화 판정"을 한다. 이전 상태로 돌아가지 않는다 🔒
활성화 판정 🔒 (시작·재개·사용자 모드 선택 때마다):
  원래 모드 LTE(NR 미포함)                                  → INACTIVE (순정, 쓰기 없음)
  원래 모드 5G 우선 ∧ 제어 불가 조건(§5.5.1 OBSERVE 행) 하나라도 → OBSERVE (쓰기 없음)
  원래 모드 5G 우선 ∧ 제어 가능                              → NR_WATCH
INACTIVE ──(사용자가 설정에서 5G 우선 선택 = 외부 USER 변경으로 NR 포함 감지)──▶ 활성화 판정
OBSERVE  ──(제어 불가 조건이 모두 해소됨, 예: S 확보 후 새 버전 기동)──▶ 활성화 판정
제어 상태(NR_GOOD·NR_WATCH·LTE_COOLDOWN·NR_PROBE·HOLD) ──(제어 불가 조건 발생, 예: 작동 표시 상실 §5.8)──▶
        현재가 원래 모드와 다르면 가드 허락 시 원래 모드로 1회 복원(가드 중에는 새 전환 없이 대기) ──▶ OBSERVE 🔒
```

- **Phase 1 시뮬레이션** (`nrctl report`): 이 상태기계를 관찰 기록에 다시 돌려 "전환했다면"을 계산한다(쓰기 없음). 정착 구간은 실제 전환이 없어 `T_settle` 고정값으로 둔다.
  - 보류(HOLD) 처리: 사유는 통화 중·통화 종료 후 `T_call_grace` 안, 화면 꺼짐(관측 공백), 로밍, USER 외 사유의 NR 제한(가드 8), 활성 SIM 2개 이상이다.
    - 보류가 시작되면 특징 창을 비운다. 보류 중 사건은 창에 넣지 않는다. 풀리면 새 창으로 시작한다.
    - 재시험 중이면 끊김 수를 비우고 평가 창을 멈춘다. 풀린 시각부터 평가 창을 다시 연다. 단 재시험 전환 뒤 정착 구간(`T_settle`)이 아직 안 끝났으면 그 끝부터 연다(정착 구간 사건은 판정에 쓰지 않음). 걸려 있던 실패 판정도 버린다.
    - USER 외 사유의 제한은 기록에 도착한 사유의 마지막 값만 쓴다(시작 시 값은 모름, §5.6.6 3번).
  - 전환하려는 순간에만 보는 가드: 서비스 없음, 예산(`B_hour`·`B_gap`).
  - 아래 두 가지는 설계 문장만으로 결론이 나지 않아 시뮬레이션이 해석을 정했다 🧪. Phase 2 구현 때 확정한다 ❓.
    1. **OOS 조건과 가드 5(서비스 없음)**: 글자 그대로면 OOS 순간 가드 5가 걸려 HOLD → 해제 때 특징 창을 비우므로 `oos_W ≥ 1` 조건이 영영 성립하지 않는다. 시뮬레이션은 "서비스 없음은 창을 비우지 않고, 복구 때 창 만료를 반영해 다시 판정"으로 해석한다. 복구가 늦어 OOS가 창(`W`)에서 벗어났으면 전환하지 않는다.
    2. **재시험 실패 판정이 서비스 없음·예산에 막힘**: 재시험 직후 끊김이 반복돼도 최소 간격(`B_gap`) 때문에 바로 LTE로 못 내린다. 재시험 중 OOS로 실패하면 그 순간은 서비스가 없다. 시뮬레이션은 "실패 판정은 유지하고, 막힘이 풀리는 때(최소 간격 경과·서비스 복구) LTE로 내림"으로 해석한다. 보류 사유에 해당하는 가드는 위 보류 처리를 따른다.
- 판정 불가 시 NR 허용 쪽으로 둔다. 데이터가 적으면 NSA 보조셀 추가 자체가 드물다는 관측(P12, 1회)에 기댄 선택이며, "무트래픽이면 플래핑 에너지 비용이 거의 없다"는 것은 **측정되지 않은 가설**이다 🧪. 실사용 기록으로 확인한다.
- 전환 판단 순서(우선순위) 🔒: ① 가드(§5.5.3) → ② 예산·최소 간격 → ③ 정착 구간 여부 → ④ 상태 전이 조건. 앞 단계에서 막히면 뒤 단계를 평가하지 않는다. 이 우선순위는 **새 전환을 허용할지 판단할 때만** 적용한다. 정착 감시(`T_settle_max` 타임아웃 포함)와 특징 기록은 이와 무관하게 항상 진행한다.
- 화면 꺼짐 중에는 **전환하지 않는다**(관측 공백, P8). `LTE_COOLDOWN` 중 화면이 꺼지면 LTE를 유지하고, 재시험은 화면이 켜진 뒤에만 한다 → 불안정 지역에서 주머니 속 대기 중에도 LTE가 유지된다.
- 쿨다운 만료 판정은 폰이 깨어 있을 때 이벤트 기반으로 한다. 데몬은 wakelock을 잡지 않는다 🔒(자는 폰을 깨워 재시험하지 않음).

#### 5.5.3 가드 (전환 금지 조건) 🔒
1. **어느 SIM이든** 통화 중·수신 중·통화 종료 후 `T_call_grace` 이내 (Telecom 수준 통화 여부 + 대상 subId 통화 상태)
2. 긴급 통화·긴급 콜백 모드
3. 외부 USER 변경 감지(§5.6.6) → USER 대기 쓰기·S2 전환 기록을 롤백 없이 닫음 + 사용자 모드 선택으로 채택 → 활성화 판정(§5.5.2: LTE면 INACTIVE, 5G 우선이면 제어 가능할 때만 NR_WATCH, 아니면 OBSERVE) + 앱 알림. 그 전환 판단 사이클의 쓰기는 하지 않는다
4. 전환 예산 소진(시간당 `B_hour`회, 최소 간격 `B_gap`)
5. 서비스 없음·비행기 모드·SIM 없음·로밍(v1은 로밍 중 비활성)
6. 대용량 트래픽 진행 중(`R_heavy` 이상) → 재시험·전환 유예
7. 관측 경로가 보조 경로(폴링)로 강등된 경우
8. USER 외 사유로 NR이 막힌 상태(§5.6.6 3번) — 제한이 풀리면 자동 해제

#### 5.5.4 백오프
`쿨다운 = min(C_base × 2^backoff_level, C_max)`. `NR_PROBE` 실패 시 레벨 +1, `T_stable` 동안 안정 시 0.

#### 5.5.5 셀 기억 (Phase 3)
- 키: LTE 앵커 셀(해시). LTE 모드에서도 관측 가능.
- 셀별 불량 점수(지수 감쇠). 불량 점수가 높은 셀에 들어오면 `N_drop`을 낮춰 빨리 쿨다운하고, 쿨다운 중 좋은/미지 셀로 바뀌면 `C_min` 경과 후 조기 재시험을 허용한다(예산 안에서).
- 위치 민감 정보이므로 폰 로컬에만 저장, 해시 처리, 외부 전송 없음 🔒.

#### 5.5.6 초기 가설 파라미터 🧪

모든 값은 설정 파일로 조정 가능하며 실사용(제어 중) 기록으로 다시 정한다. 값을 정하려고 관찰만 하는 기간은 두지 않는다(§3 개발 방식). 값이 틀려도 손해가 제한되는 근거는 전환 예산(`B_hour`·`B_gap`)과 지수 백오프다.

| 이름 | 초기값 | 근거·조정 방법 |
|---|---|---|
| `W` | 120초 | 관찰 창. 오늘 실측 플래핑 구간 약 88초가 들어가는 길이 |
| `T_active` | 2초 | active-drop 판정용 직전 데이터 활동 창 |

| `D_min`, `k` | 20초, 3표본 | 활성 중 NR 유지 중앙값 하한 |
| `T_clear` | 5분 | WATCH 해제 |
| `C_base`, `C_max` | 5분, 60분 | 쿨다운 백오프(5→10→20→40→60) |
| `C_min` | 3분 | 셀 기억 기반 조기 재시험 최소 쿨다운 |
| `P_active`, `P_max` | 데이터 사용 누적 60초, 최대 5분 | 재시험 창 |

### 5.6 실행 계층 (Actuator) — 백엔드 어댑터

#### 5.6.1 기기 자동 검사 (capability probe) 순서
1. Android 12 이상인지
2. `cmd phone help`에 get/set 명령이 있는지
3. `get -s <slot>`이 성공하는지 → **사용자 기본 마스크** 기록
4. 동일값 `set` → `completed`인지 (무부작용 권한 확인, P3)
5. 기기가 NR을 지원하는지(허용 가능한 마스크에 NR 비트 존재)
6. binder 구독(§5.3)이 가능한지
7. (선택) HAL 1.6 EN-DC 제어 가능 여부 — 백엔드 C 후보
8. **설정 화면 표시가 실제 전환을 따라가는지** — 삼성은 백엔드 S(S2) 사용 가능 여부(§5.6.5: `preferred_network_mode<subId>` 키 존재·shell 쓰기 가능·마스크↔모드 변환 짝이 삼성 기록과 일치), 그 외 기기는 백엔드 A만으로 설정 화면이 따라오는지 ❓(AOSP 설정은 USER 허용 타입을 읽는 것으로 알려져 있으나 기기별 확인 필요)
9. **상단바 작동 표시를 올릴 수 있는지** — 빌려 쓸 빈 자리가 있고 실제로 그려지는지(§5.8). 레퍼런스 기기는 `ims_volte2`(단일 SIM일 때)

결과: 모두 통과 → 제어 가능(삼성: A+S, 그 외: A) / 8번 또는 9번 실패 → **표시 일치·작동 표시 불변식 때문에 관찰 전용** / 관측만 가능 → 관찰 전용 / 제어 불가 → "미지원 기기" 보고.

#### 5.6.2 백엔드

| 백엔드 | 방법 | 사유 | 상태 |
|---|---|---|---|
| **A. 표준** | 데몬이 `/system/bin/cmd phone set-allowed-network-types-for-users -s <slot> <mask>` 실행 | USER | 실제 전환의 기본 경로. **삼성에서는 단독 사용 금지**(설정 화면이 안 바뀜, P5) 🔒 |
| **S. 삼성 표시 동기화** | 삼성 내부 동작(USER 허용 타입 변경 + `preferred_network_mode<subId>` 기록)을 shell 권한으로 재현(S2)해 **삼성 저장 모드와 USER 허용 타입을 함께** 변경 | USER | **삼성 기기 제어의 필수 조건.** 레퍼런스 기기에서 확보(§5.6.5, research §2.8). 다른 기기는 자동 검사로 확인 |
| B. POWER 사유 | binder `setAllowedNetworkTypesForReason(sub, POWER, mask)` | POWER | 보류(아래). 설정 화면에 드러나지 않아 표시 일치 원칙과도 충돌 |
| C. EN-DC 제어 | `setNrDualConnectivityState` | — | HAL 1.6+ 기기용 확장 슬롯 |

**A를 실제 전환의 기본 경로로 둔 이유**
- `cmd phone`은 Android 16 QPR2 AIDL 변경의 영향을 받지 않았다(근거 §5).
- USER 사유라 **사용자가 설정 화면에서 모드를 고르면 그 선택이 그대로 반영된다**. 레퍼런스 기기에서는 삼성 저장값과 같은 모드를 삼성 경로로 다시 적용해도(저장값 5G·실제 LTE 상태에서 5G 적용 — 이 기록의 주체는 사용자 루틴) 실제 값이 5G 포함으로 돌아왔다. 근거는 삼성 기록이며, 화면 표시는 직접 보지 않았다(research §2.5).
- 단, 삼성에서는 A만 쓰면 설정 화면이 그대로라 표시 일치 원칙을 어긴다 → S가 확보되기 전에는 삼성 기기에서 자동 제어를 하지 않는다(관찰 전용) 🔒.

**B를 보류한 이유**
- 사용자 설정을 덮지 않는 장점이 있다.
- 그러나 데몬이 NR을 끈 채 죽으면 설정 화면으로는 복구할 수 없다(교집합 때문에 USER를 바꿔도 NR이 계속 빠짐).
- 이 값도 재부팅 후 유지된다.
- 이 설계에서 확보한 복구 수단은 PC 도구와 "네트워크 설정 초기화"다(다른 주체가 POWER를 되돌릴 가능성까지 배제한 것은 아님).

#### 5.6.3 마스크 규칙 🔒
- 조작 대상은 **NR 비트(bit 19, 20자리 이진 문자열의 맨 왼쪽)** 하나. 나머지 비트는 사용자 기본 마스크 그대로 유지(엄격한 LTE-only가 통화를 깨뜨린 보고가 있음).
- NR-only 마스크는 절대 쓰지 않는다.
- 모든 쓰기 뒤에 `get`으로 USER 값 읽기 재확인. `get`은 **저장된 USER 값**을 읽을 뿐 모뎀의 실제 NR 연결을 확인하지 않는다(실제 반영은 §5.3 관측으로 본다).
- 재확인 결과별 처리 🔒 — **자동 재시도는 하지 않는다**:
  - 출력 `completed` ∧ 재확인 = 목표값 → 성공.
  - 출력 `completed` ∧ 재확인 ≠ 목표값(직전 값 포함) → NR 비트만 바꾸는 구조에서는 "쓰기 미반영"과 "사용자가 직전 값으로 되돌림"을 구분할 수 없다. 따라서 **외부 USER 변경(사용자 모드 선택)으로 처리**한다(§5.6.6 2번, §5.5.2 예외 1). USER 대기 쓰기와 열린 S2 전환 기록을 롤백 없이 닫고, 관측된 값을 새 원래 마스크로 채택한다(S2의 설정 키 기록은 이 경우 아직 하지 않은 상태다 — §5.6.5 3단계는 재확인 일치일 때만 진행). 결과가 LTE인데 직전 원래 모드가 5G 우선이었다면, 앱은 사실만 알린다. 예: "5G 우선 복귀가 확인되지 않아 컨트롤러가 멈췄습니다. 지금은 LTE입니다." 설정 화면과 실제가 일치한다는 말은 삼성 저장 모드까지 같은 모드임을 확인한 경우(§5.6.5 표시 일치 확인)에만 덧붙인다. 5G를 고르라고 요청하지는 않는다 🔒(LTE 채택 후 5G 제안 금지, §5.6.4).
  - 출력이 `completed`가 아님(`failed`·오류·빈 출력) → 전환 실패로 기록하고 재확인 값을 남긴 뒤 재시도 없이 `HOLD` + 앱 알림.
- 출력은 exit code가 아니라 문자열로 판별한다(P2). `-s <slot>` 항상 명시.
- **되돌리기 조건** 🔒: 정상 종료·`SAFE_STOP`에서 원래 마스크로 되돌리는 쓰기는 **현재 USER 값이 컨트롤러가 마지막으로 쓴 값과 같을 때만** 한다. 다르면 사용자·외부가 바꾼 것이므로 건드리지 않고 기록만 한다. 예외는 사용자가 직접 실행한 `nrctl restore`(명시적 의사)뿐이다.

#### 5.6.4 관리 모드와 기본 마스크
- **원래 마스크 확정 규칙** 🔒:
  - 폰의 상태 파일(`/data/local/tmp/nrc/state.json`)에 **정상 종료되지 않은 이전 세션**이 있으면, 현재 폰의 값이 아니라 그 세션의 원래 마스크를 **승계**한다. 현재 값은 크래시 당시 컨트롤러가 바꿔 둔 값일 수 있기 때문이다. `nrctl start`는 승계 사실을 표시한다.
  - 이전 세션이 정상 종료됐거나 상태 파일이 없을 때만 `start` 시점의 현재 USER 값을 새 원래 마스크로 저장한다.
  - 상태 파일이 손상·불일치하면 자동으로 추정하지 않고 사용자에게 원래 마스크(NR 포함/미포함)를 묻는다.
  - PC도 `start` 때 상태 파일 사본을 보관한다(폰 파일 유실 대비).
- 사용자가 외부에서 USER 값을 바꾸면(§5.6.6) 그 값이 새 원래 마스크가 된다. 이것이 사용자의 "모드 선택"이다.
- 컨트롤러는 "원래 마스크 + NR 비트 제어"를 운영 마스크로 쓴다.
- **작동 조건** 🔒: 원래 마스크에 NR이 없으면(사용자가 LTE 모드를 고름) 컨트롤러는 `INACTIVE`로 아무것도 쓰지 않는다. NR을 켜자고 제안하거나 동의를 받지도 않는다. 사용자가 설정에서 5G 우선을 고르면(외부 USER 변경으로 감지) 활성화 판정(§5.5.2)을 거친다. 제어 가능할 때만 `NR_WATCH`부터 작동하고, 제어 불가 조건이면 `OBSERVE`로 관찰만 한다.
- 정상 종료 시 원래 모드(사용자가 고른 5G 우선)로 되돌린다(§5.6.3 되돌리기 조건 적용, 삼성은 S 경로로 표시까지 함께 되돌림).
- 크래시 승계와 표시 동기화: 쿨다운 중(S로 화면·실제 모두 LTE) 데몬이 죽으면, 폰은 LTE로 일치한 채 남는다. 다음 `start`의 처리 🔒:
  - 현재 값(USER·삼성 저장 모드)이 상태 파일의 "컨트롤러가 마지막으로 쓴 값"과 **다르면** → 데몬이 없는 사이 사용자·외부가 바꾼 것이다. 현재 값을 사용자 선택으로 채택하고 되돌리지 않는다.
  - **같으면**(예: 컨트롤러가 남긴 LTE) → 컨트롤러 흔적일 수도 있고, 그 사이 사용자가 같은 LTE를 다시 골랐을 수도 있어 구분할 수 없다. 이때는 **자동으로 되돌리지 않는다.** `nrctl start`가 사용자에게 묻는다: "컨트롤러가 쉬는 중에 꺼져 LTE로 남아 있습니다. 원래 모드(5G 우선)로 되돌릴까요, 지금 LTE를 유지할까요?" 사용자가 되돌리기를 고를 때만 원래 모드로 쓴다. "LTE 유지"를 고르면 쓰기 없이 원래 모드를 LTE로 확정(상태 파일 갱신)하고 활성화 판정에 따라 `INACTIVE`로 간다.
  - 원래 마스크 확정 규칙(위)의 "승계"는 이 확인을 거친 뒤에만 쓰기로 이어진다.

#### 5.6.5 설정 화면 표시 일치 (사용자 원칙, P5)
- **요구** 🔒: 설정 화면의 네트워크 모드, 상단 표시, 실제 연결이 항상 같아야 한다. 쿨다운으로 LTE로 내릴 때는 설정 화면의 모드도 LTE가 되고, 재시험·복귀 때는 5G 우선으로 돌아가야 한다.
- 문제: `cmd phone`(백엔드 A)은 삼성 저장 모드(`preferred_network_mode`)를 갱신하지 않는다(실측: 전환 내내 값 유지). 삼성에서 A만 쓰면 요구를 어긴다.
- 해결 경로(레퍼런스 기기에서 확보): 백엔드 S = **S2**.
  - 삼성 내부의 모드 변경은 두 단계다(research §2.6).
    1. USER 허용 타입을 바꾼다.
    2. 완료 후 `preferred_network_mode<subId>`에 모드 번호를 기록한다.
  - 설정 화면은 `preferred_network_mode<subId>`를 읽어 모드를 표시한다.
  - 설정 화면을 바꾸는 삼성 통로(내부 서비스·Command SDK·내부 설정 제공자·Bixby 제공자)는 모두 삼성·시스템 앱 전용으로 막혀 있다. 그래서 **같은 두 단계를 shell 권한으로 재현**한다(`cmd phone` + `settings put global`).
- **S2 절차** 🔒:
  1. 목표 모드 번호를 얻는다. 목표 마스크를 삼성과 같은 변환(`RadioAccessFamily` 마스크↔모드 변환, hidden API)으로 바꾼다.
     - 레퍼런스 기기 관측 짝: 840583 ↔ 26, 316295 ↔ 9(research §2.2·§2.8).
     - 번호를 코드에 박지 않는다. 변환 결과가 삼성 기록의 짝과 다르거나 변환을 쓸 수 없으면 S2를 쓰지 않는다(관찰 전용). 변환 API 호출 가능 여부는 구현 시 확인 ❓.
  2. 백엔드 A로 USER 마스크를 바꾸고 §5.6.3대로 재확인한다.
  3. 출력 `completed` ∧ 재확인 일치일 때만 설정 키를 목표 모드 번호로 기록한다. 대상은 두 키로, 삼성 설정 화면 경로와 같다.
     - `preferred_network_mode<subId>`
     - 번호 없는 `preferred_network_mode`의 해당 슬롯 항목
  4. 두 키를 다시 읽는다. 어긋나면 **S2 부분 실패**로 보고 전환 전 상태로 되돌린다. USER만 되돌리면 설정 화면과 실제가 어긋난 채 남기 때문이다.
     - 1단계 전에 **전환 전 스냅샷**(USER 값, `preferred_network_mode<subId>`, `preferred_network_mode` 전체 문자열)과 **S2 전환 기록**(목표 USER 마스크·목표 모드 번호·시각)을 남긴다.
     - S2 전환 기록은 §5.6.6 1번의 "USER 대기 쓰기"와 별개다. USER 콜백으로 닫히지 않고, **두 키 확인이 끝나거나 롤백·중단 처리가 끝날 때만** 닫힌다.
     - 롤백은 **이번 전환에서 컨트롤러가 바꾼 항목만**, 항목마다 "현재 값 = 이번에 쓴 값"일 때만(§5.6.3 되돌리기 조건을 항목별로 적용) 스냅샷 값으로 되돌린다. 순서는 설정 키 → USER다(삼성과 반대 순서).
     - 롤백 USER 쓰기도 USER 대기 쓰기(목표 = 스냅샷 USER 값)로 기록한다. 그 콜백을 사용자 변경으로 오분류하지 않기 위함이다(§5.6.6 1번).
     - 롤백 후 세 값이 스냅샷과 같은 모드를 가리키면 `OBSERVE` + 알림("모드 전환 중 설정 화면 동기화에 실패해 원래대로 되돌리고 관찰만 합니다").
     - 롤백도 실패하거나 어떤 항목이 이미 다른 값(외부 변경)이면 `SAFE_STOP` + 알림. 이 경우 롤백을 이미 시도했으므로 `SAFE_STOP`의 원래 모드 복원 쓰기(§5.5.1)는 하지 않는다. 알림 예: "설정 화면과 실제 모드가 어긋났을 수 있습니다. 설정에서 원하는 모드를 한 번 고르면 맞춰집니다." 삼성 경로 선택은 두 값을 함께 쓴다(research §2.6).
- 실측(research §2.8): 레퍼런스 기기에서 S2로 **설정 화면이 5G 우선↔LTE 우선 양방향으로 따라왔다**(사용자 육안, 각 1회). 설정 키 기록 뒤 삼성 쪽의 추가 재적용 기록은 없었다.
- 미확인 ❓: 시스템 프레임워크 쪽 부작용, 다른 삼성 기기·버전, 설정 화면이 열린 채일 때의 실시간 갱신.
- 규칙 🔒: S2는 기기 자동 검사(§5.6.1 8번)에서 세 가지를 확인한 기기에서만 쓴다: 설정 키 존재, 쓰기 가능, 변환 짝 일치. S를 확보하지 못한 삼성 기기는 관찰 전용이다. 표시 불일치를 허용할지는 그때 다시 사용자 결정 사항이다.
- 표시 일치 확인 🔒: S로 쓴 뒤에는 USER 재확인(§5.6.3)에 더해, 삼성 저장 모드가 같은 모드(NR 포함 여부 일치)를 가리키는지도 확인한다. 불일치는 두 경우로 나눠 처리한다.
  - **컨트롤러의 S2 전환 중**(S2 전환 기록이 열려 있음 — USER 대기 쓰기가 이미 닫혔어도 해당): 자기 쓰기 실패다. 위 4단계의 롤백을 따른다.
  - **그 밖의 때**: 누군가 한쪽만 바꾼 외부 변경이다. §5.6.6 외부 변경 처리로 다루고 알린다. 이때 컨트롤러는 어긋남을 고치려고 쓰지 않는다.
- **상단 아이콘 수준 — 요구 범위 밖(사용자 결정, 2026-09-27)**:
  - 순정 규칙상 5G 아이콘은 NR이 실제로 연결되지 않고 "대기 중 사용 가능"일 때도 뜬다(P6, 레퍼런스 기기 실측).
  - 예: 5G 우선 모드에서 폰이 쉬고 있으면 실제 5G 연결이 없어도 아이콘은 5G다. 이는 컨트롤러가 없어도 생기는 순정 동작이다.
  - 사용자는 "모드는 일치"를 요구하고, 아이콘 규칙은 바꾸지 않기로 했다. 순정 동작 유지다.
  - 대신 컨트롤러가 제어 중임을 알 수 있도록 **상단바 작동 표시**를 둔다(§5.8).
  - 이 설계는 백엔드 S로 **모드(5G 우선 / LTE) 수준** 일치를 보장하는 것을 목표로 한다. 아이콘이 실제 NR 연결만 반영한다고 주장하지 않는다.

#### 5.6.6 외부 변경 처리 (사유 구분·자기 쓰기 대조) 🔒
허용 타입 변경 콜백은 (사유, 그 사유의 마스크)를 전달한다(AOSP Phone.java·TelephonyRegistry). 이를 다음처럼 구분한다.

데몬은 "현재 알고 있는 USER 값"과 "USER 외 사유별 마지막 값"을 따로 유지한다.

1. **자기 쓰기 대조**: 데몬은 USER 쓰기 직전에 "USER 대기 쓰기(목표 마스크, 시각)"를 기록한다. USER 사유 콜백의 마스크가 목표 마스크와 같고 대기 시간 안에 오면 자기 쓰기로 보고 USER 대기 쓰기를 닫는다. 현재 알고 있는 USER 값과 같은 콜백(중복·지연 도착한 자기 쓰기 알림)은 무시한다.
   - USER 대기 쓰기를 닫는 것은 **USER 변경 확인일 뿐**이다. 백엔드 S의 **S2 전환 기록**(§5.6.5 4단계)은 이와 별개로, 두 키 확인 또는 롤백·중단 처리가 끝날 때까지 열려 있다.
   - **자기 콜백 판정 기준은 "지금 진행 중인 컨트롤러 USER 쓰기의 목표"**다. S2 정방향 단계에서는 S2 목표 마스크, 롤백 단계에서는 스냅샷 USER 값(롤백 목표)이 기준이다. 롤백 USER 쓰기도 USER 대기 쓰기로 기록한다(§5.6.5 4단계). 이 목표와 같은 USER 콜백은 롤백 콜백을 포함해 자기 쓰기다.
   - S2 전환 기록이 열려 있는 동안 관측되는 설정 키 변화도 자기 전환의 일부로 본다. 대상은 컨트롤러가 기록 중이거나 롤백 중인 값이다. 외부 변경으로 판정하지 않는다.
   - 늦게 도착한 콜백도 자기 쓰기로 본다. S2 전환 기록이 열려 있는 동안 도착한 콜백의 값이 **이번 전환에서 컨트롤러가 이미 완료한 USER 쓰기 값**(예: 롤백 중에 뒤늦게 온 정방향 콜백)과 같으면 자기 쓰기다.
   - S2 전환 기록이 열려 있는 동안 **현재 진행 중인 USER 쓰기 목표와도, 이번 전환에서 컨트롤러가 쓴 어떤 USER 값과도 다른** USER 콜백만 사용자·외부 변경이다. 2번으로 처리하고, 두 기록을 롤백 없이 닫는다(사용자 선택 존중).
2. **외부 USER 변경 = 사용자 모드 선택**: USER 사유 콜백의 마스크가 현재 알고 있는 USER 값과 다르고 대기 중 목표와도 다를 때.
   - USER 대기 쓰기와, 열려 있으면 S2 전환 기록도 **롤백 없이** 닫는다(자동 재시도는 원래 없음, §5.6.3). 사용자 선택을 되돌리지 않기 위함이다.
   - 그 값을 새 원래 마스크로 채택하고, 특징 창을 비운 뒤 **활성화 판정(§5.5.2)을 호출**한다. LTE면 `INACTIVE`, 5G 우선이면 제어 가능할 때만 `NR_WATCH`, 제어 불가 조건이면 `OBSERVE`다(§5.5.2 예외 1). 사용자 재개는 필요 없다. 모드 선택이 곧 스위치다.
   - 사람이 설정에서 고른 것과 삼성 루틴 같은 자동화가 바꾼 것은 같은 삼성 경로를 거쳐 구분되지 않는다. 둘 다 사용자 의사로 존중한다. 모드를 바꾸는 루틴이 컨트롤러와 겹치면 앱이 "모드를 바꾸는 루틴이 있으면 컨트롤러가 자주 멈출 수 있음"을 안내한다(research §2.5: 핫스팟 켜면 5G로 바꾸는 루틴 사례).
   - **같은 값 재선택은 감지되지 않을 수 있다** ❓. 쿨다운 중(설정 화면·실제 모두 LTE) 사용자가 설정에서 LTE를 다시 골라도 값이 같아 콜백이 없거나(중복 콜백은 1번 규칙으로 무시), 컨트롤러가 사용자 의사와 자기 흔적을 구분하지 못한다. 그러면 쿨다운 만료 후 재시험이 사용자 의사를 덮어쓸 수 있다. 보완 🔒:
     - 쿨다운에 들어갈 때 앱 알림에 **"LTE로 계속 쓰기"** 버튼을 둔다(빠른설정 타일에도 같은 동작). 이 버튼을 누르면 사용자 LTE 선택으로 확정한다. 이미 설정 화면·실제 모두 LTE이므로 추가 쓰기 없이 원래 모드를 LTE로 바꾸고 INACTIVE로 간다. 이후 재시험·5G 복귀 쓰기를 하지 않는다.
     - 재시험(5G 복귀) 직전 화면이 켜져 있으면 알림으로 "잠시 후 5G 우선으로 되돌립니다" 사실을 알린다. 버튼을 누를 기회를 주기 위함이다.
     - 설정 화면의 같은 값 재선택을 관측할 수단(예: 삼성 경로 호출 기록·설정 변경 알림이 같은 값에도 발생하는지)은 Phase 0 ⑥에서 확인한다. 확인 전까지 "설정 화면에서 LTE를 다시 누르면 반영된다"고 안내하지 않는다.
     - **기기 실측(2026-09-28 20:24, research §2.12)**: 쿨다운 중 사용자가 설정에서 LTE 우선을 누르자 값이 같은데도 USER 알림이 왔다(자기 쓰기 47초 뒤). 컨트롤러는 같은 값이라 무시했고, 쿨다운 만료 재시험이 5G로 덮어썼다(결함). 자기 쓰기 알림은 쓰기 끝 0.002~0.32초 안(7건). → §5.11 결정 18로 감지한다. 이번 사례는 설정 화면이 예전 값(5G 우선)을 보여 주던 때라 삼성이 "변경"으로 처리했다. **화면이 이미 LTE로 보일 때 같은 항목을 누르면 삼성이 아무것도 쓰지 않고 알림도 없다**(기기 실측 20:54~56, 수정본). 이 경우는 설정 화면으로 감지할 수 없으므로, 위 보완(알림의 "LTE로 계속" 버튼·재시험 전 알림)이 유일한 폰 안의 수단이다(동반 앱 기능 필요).
3. **USER 이외 사유(CARRIER·POWER·ENABLE_2G 등) 변경**: 사용자 기본값으로 **채택하지 않는다**. 이 값을 USER 쓰기에 섞지 않는다(USER 마스크는 항상 원래 USER 마스크 기준으로 만든다).
   - **외부 제한 판정은 USER를 제외하고 한다**: USER 외 사유들의 마지막 값의 교집합에 NR 비트가 없으면 "외부 제한으로 NR 불가". 쿨다운 중 컨트롤러가 USER에서 NR을 뺀 것은 외부 제한으로 보지 않는다.
   - 외부 제한이 생기면 `HOLD`(쓰기 중단), 외부 제한이 풀리면 **자동으로** 이전 상태로 돌아간다(특징 창 초기화). 이 보류는 사용자 의사가 아니므로 사용자 재개를 요구하지 않는다.
   - 시작 시 사유별 초기값 확보 ❓: 사유별 조회 API는 한 번도 설정되지 않은 사유에 기본값을 돌려줄 수 있어(AOSP) 그대로 믿을 수 없다. 허용 타입 알림도 등록 시 현재값을 보내지 않았다(레퍼런스 기기 7회 기동, §5.3 Phase 1 구현). 그래서 v1은 콜백이 도착한 사유만 판정에 쓰고, 시작 시 USER 외 사유는 "모름"으로 둔다.
4. 콜백이 재확인보다 늦게 도착할 수 있으므로, 출력이 `completed`이고 재확인 값이 목표와 다르면 콜백을 기다리지 않고 2번으로 처리한다(§5.6.3). 출력이 `completed`가 아니면 원래 마스크를 바꾸지 않고 §5.6.3의 명령 실패 처리를 따른다.

### 5.7 안전·복구

| 상황 | 결과 | 복구 경로 |
|---|---|---|
| 데몬이 NR 비허용 상태에서 종료(크래시·adbd 재시작·USB 디버깅 끄기) | LTE 모드로 남음. 통신은 정상이고 5G만 없다. 삼성은 S로 설정 화면도 LTE로 일치한 상태 | ① 앱이 데몬 부재 감지 → 사실 알림("컨트롤러가 쉬는 중에 꺼져 LTE로 남아 있음, 원래 모드는 5G 우선") ② `nrctl restore` 또는 `nrctl start`(현재 값 대조 + 사용자 확인 후에만 되돌림, §5.6.4) ③ 사용자가 원하면 설정 화면에서 모드 선택(삼성 경로 적용은 반영됨 — 레퍼런스 기기 삼성 기록, research §2.5) |
| 재부팅 | 데몬 종료. **재부팅 시 USER 허용 타입(DB)이 적용되고 삼성 저장 모드는 재적용되지 않는다**(실측, research §2.5). S로 표시를 맞춰 두었다면 쿨다운 중 재부팅해도 화면·실제 모두 LTE로 일치 | 앱이 부팅 완료 시 사실 알림("컨트롤러 꺼짐, 쉬는 중 LTE로 남았을 수 있음, 원래 모드는 5G 우선, 재기동은 PC 연결 필요") |
| 외부 USER 변경(사용자·루틴이 설정 경로로 모드 변경) | USER 대기 쓰기·S2 전환 기록을 롤백 없이 닫음, 사용자 모드 선택으로 채택 → 활성화 판정(§5.5.2) | 자동(모드 선택이 스위치) |

| USER 이외 사유 변경(통신사 등) | 기록. USER 제외 교집합에 NR이 없으면 `HOLD` | 제한이 풀리면 자동 복귀 |
| 크래시 후 재기동 | 이전 세션의 원래 마스크 승계(§5.6.4) | `nrctl start`가 승계 표시 |
| 출력 `completed` ∧ 재확인 값 ≠ 목표값 | 사용자 모드 선택으로 처리(관측값 채택 → 활성화 판정), 재시도 없음 | 자동. 원래 5G 우선이었는데 LTE로 남았다면 사실만 알림(5G 선택 요청 없음, §5.6.3) |
| 명령 출력이 `completed` 아님 | 재시도 없이 `HOLD` + 알림 | 사용자가 재개 |
| 정착 확인 시간 초과(`T_settle_max`) | `SAFE_STOP`: 현재 USER 값이 컨트롤러가 마지막으로 쓴 값일 때만 원래 마스크로 되돌리고 정지 | 앱·CLI 경고 |
| 전화 프로세스 재시작 | 알림 등록은 system_server의 레지스트리에 있어 유지된다(소스, §5.3) | 기록만(`phone_died`). 레지스트리(system_server) 종료는 구독이 끊기므로 데몬이 기록 후 종료 → 재기동 필요 |

추가 불변식 🔒
- 데몬은 상태 파일에 "원래 마스크 / 마지막으로 쓴 마스크 / 현재 상태"를 쓰기 전에 먼저 기록한다(크래시 후 `nrctl restore`의 근거).
- 네트워크 소켓을 열지 않는다(원격 제어면 없음).
- 데몬이 쓰는 파일은 `/data/local/tmp/nrc/` 아래로 한정한다.

### 5.8 동반 앱

- minSdk 31(Android 12, `cmd phone` 명령 존재 기준), 사이드로드 설치(PC 도구가 `adb install`).
- **데몬 ↔ 앱 통신 (Shizuku와 같은 검증된 패턴)**
  - 데몬이 앱의 ContentProvider를 호출해 자신의 binder를 전달하고, 앱은 그 binder로 AIDL을 호출한다.
  - 데몬은 모든 호출에서 `Binder.getCallingUid()`가 동반 앱 uid인지 검사한다 🔒.
  - Provider는 `call()` 진입 시 **호출 uid가 shell(2000)·system(1000)인지 명시적으로 검사**한다 🔒. 매니페스트 권한(예: `DUMP` 보유 요구)은 보조 계층일 뿐이다. `DUMP`는 `signature|privileged|development` 보호 수준이라 shell·system 전용을 보장하지 않는다.
  - 대안인 abstract unix socket은 SELinux상 앱→shell 연결 허용 여부가 미확인이라 채택하지 않는다.
- **알림**: 데몬이 상태 변화 시 Provider를 호출해 앱을 깨우고, 앱이 알림을 게시한다. 상시 포그라운드 서비스는 두지 않는다.
- **빠른설정 타일**: 자동(컨트롤러 작동) / LTE로 계속 쓰기(쿨다운 중에만 활성. 이미 설정 화면·실제 모두 LTE이므로 추가 쓰기 없이 원래 모드를 LTE로 확정 → INACTIVE, §5.6.6) / 일시정지(쓰기 중단·현재 상태 유지). 5G를 켜는 버튼은 두지 않는다(5G 우선은 사용자가 설정에서 고름). 모든 동작은 가드(통화 등)를 따른다.
- **데몬 부재 감지**: 앱 실행·타일 사용·부팅 완료 시 binder 연결 확인. 연결이 없으면 안내 알림.
- **표시 정보**: 현재 상태(양호/경계/쿨다운 n분 남음/재시험/보류), 실제 NR 허용 여부, 오늘 전환 횟수와 누적 추정 단절 시간, 최근 이벤트.

#### 상단바 작동 표시 (사용자 요구, 2026-09-27)
- **요구**: 5G 우선 모드에서 컨트롤러가 제어 중이면, 사용자가 상단바의 5G/LTE 표시 근처에서 알 수 있어야 한다(예: 점). 알림창을 띄우는 방식이 아니다.
- **방법**: 데몬(shell 권한)이 상단바 서비스에 아이콘을 올린다(`IStatusBarService.setIcon(slot, 패키지, 아이콘 id, 레벨, 설명)` / `removeIcon(slot)`). 레퍼런스 기기에서 shell은 `STATUS_BAR` 권한을 보유했다(research §2.7).
- **레퍼런스 기기 시험 결과**(research §2.7):
  - **위치 — 새 이름의 자리는 안 보임**: `nrc_active` 같은 새 자리는 상단바 서비스에는 "보임"으로 등록되지만 삼성 상단바에 그려지지 않았다(사용자 육안 + 상단바 캡처).
  - **위치 — 빈 SIM2 VoLTE 자리는 보임**: 이 기기에서 비어 있는 두 번째 SIM의 VoLTE 자리(`ims_volte2`)에 올리면 **신호 막대 바로 오른쪽(배터리 앞)**, 즉 5G/LTE 표시 바로 옆에 그려졌다.
  - **색**: 삼성 상단바가 아이콘을 한 가지 색으로 칠해 초록색이 흰색으로 보였다. 색으로 구분하는 표시는 불가로 보고 모양으로 구분한다.
  - **크기**: 시험에 쓴 기본 아이콘은 자리를 꽉 채워 큰 원으로 보였다. 구현에서는 동반 앱에 "작은 점 + 투명 여백" 아이콘을 넣어 작게 만든다(❓ 실제 크기는 구현 시 확인).
- **표시 조건** 🔒: 컨트롤러가 실제로 제어 중인 상태(`NR_GOOD`·`NR_WATCH`·`LTE_COOLDOWN`·`NR_PROBE`)에서만 표시한다. `INACTIVE`(사용자 LTE)·`OBSERVE`(관찰만)·정지 상태에서는 표시하지 않는다. `HOLD` 중에는 표시를 유지한다(§5.11 결정 6).
- **표시 없이는 제어하지 않는다** 🔒: 작동 표시를 올릴 수 없거나(자리 없음·사용 중·기기 미지원) 올린 표시를 잃으면(시스템이 자리를 덮어씀 등), 이를 **제어 불가 조건**으로 본다(§5.5.1 OBSERVE 행).
  - 제어 중이 아니었다면(활성화 판정 시점) `NR_WATCH`로 가지 않고 `OBSERVE`로 간다.
  - 제어 중에 표시를 잃었고 `LTE_COOLDOWN` 등으로 원래 모드와 다른 상태라면: 가드(§5.5.3)가 허락하는 즉시 원래 모드(5G 우선)로 되돌리는 쓰기 **한 번만** 하고 `OBSERVE`로 간다. 이 복원은 사용자의 원래 선택으로 돌려놓는 것이며, 이후 추가 쓰기는 없다.
  - 가드 때문에 즉시 되돌리지 못하는 동안(예: 통화 중)에는 새 전환을 하지 않고, 가드가 풀리면 위 복원을 한다.
- **자리 사용 규칙** 🔒:
  - 빌려 쓰는 자리(`ims_volte2`)는 두 번째 SIM이 없을 때만 쓴다. v1 자동 제어가 단일 SIM에서만 동작하므로(§6) 이 조건과 일치한다.
  - 올리기 전에 그 자리가 비어 있는지 확인하고, 시스템이 쓰고 있으면 올리지 않는다.
  - 지울 때는 그 자리 아이콘이 컨트롤러가 올린 것(패키지·아이콘 id)일 때만 지운다.
  - 시스템이 그 자리를 덮어쓰면 양보하고 다시 올리지 않는다.
  - 자리 이름·위치는 제조사·버전마다 다를 수 있으므로 기기 자동 검사(§5.6.1)에서 확인한다.
- **남는 점 위험** ❓: 상단바 아이콘은 올린 프로세스가 죽어도 시스템에 남는다(재부팅 시 사라짐으로 추정). 데몬이 갑자기 죽으면 **제어 중이 아닌데 점이 남아** 작동 중처럼 보일 수 있다. 보완 🔒:
  - 정상 종료·`SAFE_STOP`·`nrctl stop/restore`에서 반드시 지운다.
  - `nrctl start`·`doctor`는 이전 세션이 남긴 점을 소유 확인 후 지운다.
  - 동반 앱이 데몬 부재를 감지하면 "상단바 점이 남아 있을 수 있음(PC 연결로 정리. 재부팅으로 사라지는지는 아직 확인 안 됨)"을 알린다. 앱에는 상단바 권한이 없어 직접 지울 수 없다.
  - 재부팅 시 사라지는지는 구현 시 확인한다.

### 5.9 PC 도구 `nrctl`

- 언어: **Python 3.11+** (Windows·macOS 공통, 이후 단일 실행파일로 패키징).
  - 이 PC에 Python이 있고 분석·리포트 작성이 쉬워서 택했다. 대안은 Go 단일 바이너리로, 배포가 쉬운 대신 개발 속도가 느리다.
- adb: 사용자가 설치한 platform-tools를 탐지하거나 경로를 지정한다.
- Windows 경로 처리는 테스트 항목으로 둔다. 비ASCII 경로(예: `…\Downloads\프로그램\platform-tools`)와 **대괄호가 든 경로**(예: 이 프로젝트 폴더 `[LTE-5G] …`)가 대상이다.
  - 이번 작업 중 관측된 실패(콘솔 출력 원문 보관, research §2.4): PowerShell 5.1은 대괄호 경로의 스크립트 실행이 와일드카드 오류로 실패했고, Git Bash는 `/d/...` 경로를 Windows 프로그램 인자로 잘못 변환했다.
  - 따라서 경로는 셸 문자열로 조립하지 않고, 인자 배열과 글자 그대로의 경로로 넘긴다 🔒.

| 명령 | 동작 |
|---|---|
| `doctor` | 기기 연결·USB 디버깅·Auto Blocker 안내·capability probe(§5.6.1) 보고서 |
| `install` | 동반 앱 APK 설치 |
| `start [--observe]` | 데몬 기동(기본은 Phase에 맞춰 관찰 전용), 원래 마스크 확정(§5.6.4 — 미완료 이전 세션이면 승계) |
| `stop` | 정상 종료 + 원래 모드(사용자가 고른 모드)로 복원. 현재 값이 컨트롤러가 쓴 값일 때만 복원한다(§5.6.3). NR을 켜는 복원 선택지는 두지 않는다 |
| `status` | 데몬 상태·현재 마스크·최근 이벤트 |
| `pause` / `resume` / `keep-lte` | 수동 제어. `keep-lte`는 쿨다운 중 "LTE로 계속 쓰기"다. 추가 쓰기 없이 원래 모드를 LTE로 확정하고 INACTIVE로 간다. 5G를 켜는 명령은 두지 않는다. 5G 우선은 사용자가 설정에서 고른다(§5.6.4) |
| `restore` | **긴급 복구**: 상태 파일의 원래 마스크로 `set` + 재확인(데몬 없이도 동작) |
| `pull` / `report` | 로그 수집·집계(시간당 활성 끊김, 쿨다운 시간, 전환 횟수와 비용, 배터리) |
| `observe` | PC 상주 진단 모드(폴링, 관찰 전용, 정확도 낮음 — §5.3 보조 경로) |
| `measure` | A/B 측정 절차 보조(§9) |

**Phase 1 구현 상태 (2026-09-28)** — `pc/nrctl.py`(Python 3.8+ 표준 라이브러리), 시험 `pc/test_nrctl.py`
- 구현: `doctor`(읽기 전용 점검) · `start`(관찰 전용 기동) · `stop` · `status` · `pull`(폰 기록을 기기별 합본 파일에 중복 없이 누적) · `report`(요약 + "전환했다면" 시뮬레이션, 기준값은 옵션으로 변경).
- Phase 1의 `nrctl`에는 네트워크 설정을 바꾸는 명령이 없다. `start`의 원래 마스크 확정·승계와 `stop`의 복원은 쓰기가 생기는 Phase 2부터 해당한다. 나머지 명령(`install`·`pause`·`resume`·`keep-lte`·`restore`·`observe`·`measure`)도 Phase 2 이후에 만든다.
- `stop`은 종료 요청 파일(`stop.req`)에 **대상 pid**를 적는다. 🔒 PC 도구는 프로세스 번호로 신호를 보내지 않는다. 확인과 신호 사이에 그 번호가 다른 프로세스로 바뀌면 엉뚱한 작업을 끌 수 있기 때문이다.
  - 데몬은 파일 변화 알림으로 요청을 받는다. 적힌 pid가 자기일 때만 처리하고, 다른 실행을 겨냥한 늦은 요청은 무시한다.
  - 처리: 작업 스레드가 열린 데이터 사용 구간을 닫고 `stopped`(by=request, pid)를 남긴 뒤 끝난다. 작업 스레드가 5초 안에 못 하면(멈춤) 기록 없이 스스로 끝난다.
  - 12초 안에 끝나지 않으면(요청 감시까지 멈춘 경우) PC는 실패를 알리고 재시도 또는 폰 재부팅을 안내한다. 관찰 전용이라 되돌릴 설정은 없다. 이때 pid 파일은 **남긴다**(status가 계속 실행 중으로 보이고 stop을 다시 할 수 있게).
  - 요청 파일·pid 파일은 종료가 확인된 뒤에만, 아직 그 pid를 가리킬 때만 지운다.
  - 리포트는 pid가 적힌 종료 기록이 그 세션의 시작 pid와 다르면 세션을 닫지 않는다(이전 버전이 덧붙인 기록 대비).
  - 실측(research §2.9): 요청 종료 확인, 다른 pid를 적은 요청 무시 확인. 작업 스레드 멈춤 시의 자체 종료는 기기에서 재현하지 않았다 ❓.

### 5.10 로그 (Journal)
- JSONL, 크기 상한과 순환 적용. 레코드 종류: 이벤트 원시값(요약), 특징, 상태 전이(사유 포함), 전환(전·후 마스크, 출력, 재확인, 이후 OOS·IMS 공백 추정), 가드 발동, 관측 공백.
- 셀 식별자는 해시로 저장한다. 외부 전송은 없고, PC `pull`로만 가져간다 🔒.
- 스키마 버전 필드를 둔다(PC 리포트 호환용).
- Phase 1 레코드(스키마 1, 공통 필드 `t`=기록 시각 ms, `ev`=종류):
  - 수명: `start`(버전·기기·subId·활성 SIM 수) · `registered`(허용 타입 알림 여부) · `first`(알림 종류별 첫 수신) · `alive`(깨어 있는 10분마다) · `stopped`(by=request + pid. 과거 기록에는 이전 버전 nrctl이 덧붙인 by=nrctl·nrctl-kill도 있다) · `warn` · `error` · `fatal` · `phone_died`
  - 관측: `nr_on`/`nr_off`(마지막 데이터 활동 후 경과·NR 유지 시간·화면) · `ss`(nrState·데이터/음성 등록·RAT·로밍) · `oos`/`service` · `pcc`(NR 보조셀 유무·셀 목록) · `sig`(LTE rsrp, NR ss-rsrp/sinr. NR 신호가 생기거나 사라지면 즉시, 그 밖에는 LTE rsrp가 5dB 구간을 넘고 직전 기록 뒤 10초 이상일 때만. 알림이 와도 이 조건이 아니면 기록하지 않는다) · `data`(사용 구간 시작·길이. 30초 주기마다 지금까지의 조각을 기록하고 종료 요청 때 닫는다. 정상 주기라면 갑자기 끝날 때 잃는 양은 약 한 주기(깨어 있는 30초)이며, 작업이 늦어지면 그만큼 늘 수 있다) · `call` · `screen` · `mode`(USER 마스크) · `allowed`(사유·마스크) · `display`(기록 전용) · `thermal`
- 폰 쪽은 `nrd.log`가 4MB를 넘으면 순환한다(최근 3개). PC `pull`이 합본(`logs/<기기>/nrd-merged.jsonl`)에 누적하므로 순환 전에 가져오면 잃지 않는다.

### 5.11 Phase 2 구현 (2026-09-28, 레퍼런스 기기 시험)

설계를 코드로 옮기면서 정한 것과 기기 시험에서 바뀐 것을 모았다. 코드는 `daemon/src/nrc/`, PC 도구는 `pc/nrctl.py`, 동반 앱은 `app/`.

**구성**
| 부품 | 역할 |
|---|---|
| `Policy` | 상태기계(§5.5). 안드로이드와 무관한 순수 코드라 PC에서 시험한다(`bash daemon/test.sh`, 판정 86개). 규칙은 `nrctl report` 시뮬레이션과 같다 |
| `Actuator` | 백엔드 S2(§5.6.5). **폰 설정을 바꾸는 데몬 코드는 여기에만 있다**(그 밖에는 사용자가 직접 실행하는 `nrctl restore`뿐). 폰 입출력을 `Io`로 받아 가짜 폰으로 PC 시험한다(판정 29개). 외부 명령은 셸을 거치지 않고 인자 배열로 실행하고 15초 제한을 둔다(`Exec`) |
| `Controller` | 관찰 사건 → 정책, 원래 모드·사용자 변경 감지, 상단바 표시, 상태 파일 |
| `Indicator` | 상단바 점(§5.8) |
| `StateStore`·`Saved` | 상태 파일 `state.json`: 원래 마스크·모드 번호, 컨트롤러가 **지금도 남겨 둔 값**(`lastWritten`), 쓰기 직전 선기록한 **시도 값**(`pending`), 상태, 정상 종료 여부, subId·슬롯. 임시 파일에 쓰고 이름을 바꾼다. 쓰기 결과 반영·다음 시작의 원래 모드 확정 규칙은 `Saved`에 두고 PC에서 시험한다(판정 18개) |

**설계 해석·결정(구현 중 확정)** 🔒
1. **사용자 모드 변경 뒤의 조용한 구간**(기기 시험에서 발견·수정): 사용자가 설정에서 5G 우선을 고르면 폰이 망에 다시 붙으며 데이터가 1.6초 끊겼다. 컨트롤러가 이를 불안정 신호로 세어 4초 만에 LTE로 내렸다. 이제 사용자 모드 변경 뒤에도 컨트롤러 쓰기 뒤와 같은 정착 구간을 둔다. 이 구간의 끊김은 판정에 세지 않는다. 컨트롤러가 쓴 것이 아니므로 시간 초과는 SAFE_STOP이 아니라 그냥 끝낸다. 컨트롤러 시작 직후에도 같은 조용한 구간을 둔다(종료 때 되돌리기 직후 다시 켜는 경우 대비). `nrctl report` 시뮬레이션에도 사용자 모드 변경 뒤 규칙을 넣었다.
2. **정착 시계는 쓰기를 끝낸 시각부터**(기기 시험에서 발견·수정): 판정 시각부터 재면 쓰기에 걸린 시간(대용량 확인 1초 + S2 약 0.6초)만큼 정상 확인이 앞당겨졌다. 그러면 전환 직후의 끊김보다 먼저 "정상"으로 확인됐다. 비용 기록(`switch_cost`: 끊긴 시간·회복 시각·확인 시각)도 정착이 끝날 때 남긴다.
3. **원래 모드로 되돌리는 쓰기의 가드**: 제어 불가 발생·SAFE_STOP·종료 때의 되돌리기는 통화(유예 포함)만 막는다. 사용자가 고른 모드로 돌아가는 일을 예산·화면 상태로 늦추지 않기 위해서다. 새 전환(LTE로 내림·재시험)은 모든 가드를 따른다.
4. **§5.5.2의 두 해석(Phase 1 시뮬레이션)을 엔진에도 적용**했다: 서비스 없음은 창을 비우지 않고 복구 때 다시 판정한다. 재시험 실패 판정은 서비스 없음·예산·대용량 트래픽·정착에 막히면 유지했다가 풀릴 때 실행한다.
5. **사용자 변경 감지**(§5.6.6): 허용 타입 알림은 계기로만 쓰고, 지금 USER 값을 다시 읽어 컨트롤러가 알고 있는 값과 비교한다. 쓰기는 작업 스레드에서 동기로 끝나고 그때 확인값으로 갱신되므로, 늦게 온 자기 쓰기 알림은 비교에서 걸러진다. 기기 시험에서 사용자의 5G 우선·LTE 우선 선택을 모두 알림으로 즉시 감지했다.
6. **HOLD 중 작동 표시**: 유지한다. 보류 중에도 컨트롤러가 정한 모드(예: 쉬는 중 LTE)가 유지되기 때문이다(§5.8의 ❓ 결정). 예외: Wi-Fi 보류는 숨긴다(17번).
7. **이전 세션이 남긴 LTE**(§5.6.4): 데몬이 거부하고 `nrctl start`가 사용자에게 되돌리기/유지를 묻는다(대화형이 아니면 `--leftover`). 상태 파일이 손상되면 `--original=nr|lte`로 원래 모드를 받는다.
8. **시험용 명령** `nrctl test-cooldown`: 불안정 지역 없이 전환 경로를 확인하려고 끊김 조건만 건너뛰고 LTE로 2분 쉬게 한다. 가드·예산·정착은 평소와 같다.
9. **통화 확인은 쓰기 바로 앞에서**(검증에서 발견): 가드 순서를 보류 → 서비스 → 예산 → 정착 → 대용량 트래픽(1초 측정) → 통화로 둔다. `Actuator`가 준비(설정 조회·상태 파일 선기록)를 모두 마친 뒤 USER 쓰기 명령 바로 앞에서 한 번 더 통화를 확인한다. 막히면 쓰기 없이 `BLOCKED`로 돌아가 가드 막힘과 같게 처리한다.
10. **쿨다운 중(LTE) 끊김은 5G 품질 사건이 아니다**: 쿨다운 중 OOS·끊김은 판정에 넣지 않는다(넣으면 경계 상태로 바뀌어 재시험을 잃었다).
11. **재시험 사용 시간**: 기록·시뮬레이션과 같은 규칙으로 3초 이하 멈춤은 사용으로 센다. 보류가 풀려 평가 창을 다시 열 때 누적도 새로 시작한다.
12. **막힌 전환의 재확인 간격**: 시간으로 풀리지 않는 이유(통화 조회 실패·서비스 없음 등)로 막히면 30초 뒤 다시 본다(사건이 오면 그때 바로). 처리하고도 남은 지난 예약은 5초 간격으로만 다시 본다(쉬지 않는 반복 방지).
13. **종료 때 되돌리기 실패**: 종료는 하되 정상 종료로 저장하지 않는다. 상태 파일은 시도 값(`pending`)과 지금도 남겨 둔 값(`lastWritten`)을 따로 둔다. USER가 실제로 바뀐 것을 확인하는 즉시 `lastWritten`에 기록한다(이후 설정 키 쓰기·롤백 선기록 중에 멈춰도 흔적을 잃지 않게). 롤백에 성공하면 거래 전 값으로 되돌리고, 실패·막힘이면 적용된 흔적을 그대로 둔다. 다음 시작은 비정상 종료 + 지금 값 ≠ 원래 모드 + 지금 값이 `lastWritten` 또는 `pending`과 같으면 "컨트롤러가 남긴 LTE"로 판정해 사용자에게 묻는다.
14. **S2 도중 사용자 선택**: 설정 키를 쓴 뒤 USER를 다시 읽는다. 그 사이 사용자가 모드를 골랐으면(삼성 경로가 USER와 키를 함께 바꿈) 방금 덮은 키를 사용자 값에 맞는 번호로 되돌리고 사용자 선택으로 채택한다. 덮은 키를 맞추지 못하면 사용자 선택은 원래 모드로 채택하되, 화면이 어긋난 채라 제어를 안전 정지한다(추가 쓰기 없음). 롤백 USER 쓰기도 선기록이 실패하거나 통화 중이면 쓰지 않는다(→ SAFE_STOP, 남은 값은 흔적으로 기록).
15. **상단바 표시 상실**: 표시 중이던 자리가 비거나 남의 것이 되면, 주기 점검 전이라도 다시 올리지 않고 제어 불가로 넘긴다.
16. **S2 판정 기준은 재확인 값**: `cmd` 출력이 `completed`가 아니어도(예: 응답 시간 초과) USER가 목표로 바뀌었으면 적용된 것으로 보고 설정 키까지 맞춘다(표시 일치 우선). §5.6.3의 "출력이 completed가 아님 → 실패"는 USER가 바뀌지 않은 경우(이전 값 그대로·읽기 실패)로 한정한다. 이전 값과도 목표와도 다르면 사용자 선택으로 채택한다.
17. **Wi-Fi 보류와 원래 설정 되돌리기**(사용 중 사용자 발견·결정, 2026-09-28): 기본 인터넷 경로가 Wi-Fi(셀룰러 아님)면 보류 사유 `wifi`로 판단을 쉬고 작동 표시를 숨긴다(6번의 예외: 다른 보류는 표시 유지). 감지는 기본 네트워크 콜백(`NetWatch`, 숨은 `ConnectivityManager` 생성자 + shell 컨텍스트, 기기 확인). 보류 우선순위는 통화 다음이다.
    - 표시는 보류 사유가 아니라 Wi-Fi 여부를 따른다. Wi-Fi 중 통화가 와서 보류 사유가 `call`이 돼도 점을 다시 띄우지 않는다.
    - 감시 등록에 실패하면 셀룰러로 가정하지 않고 제어 불가(`wifi_watch_unavailable`, 관찰만)로 둔다.
    - 컨트롤러가 LTE로 쉬게 해 둔 상태(COOLDOWN·NR 비허용·원래 5G 우선)에서 Wi-Fi 보류가 되면 **사용자의 원래 모드로 되돌린다**. 되돌리기 가드는 3번과 같이 통화만(유예 포함). 되돌린 뒤 WATCH로 두고, Wi-Fi가 끊기면 평소 규칙으로 판단한다.
    - **원래 LTE 우선이면 쓰지 않는다**(사용자 강조: Wi-Fi에서 모바일로 돌아왔을 때 LTE 사용자를 5G로 강제하지 않는다). 쓰는 값은 언제나 원래 모드 기준 마스크이고, 원래 LTE면 컨트롤러는 INACTIVE라 이 경로에 들어오지 않는다. 쉬는 중 사용자가 LTE를 고른 것이 **감지되면**(값이 바뀐 경우) 원래 모드가 LTE로 바뀌므로 되돌리지 않는다.
    - 쉬는 중 같은 LTE를 다시 고른 경우: 결정 18로 감지한다(알림이 오는 경우에 한함, §5.6.6 2번).
    - 일시정지·명령 실패 보류 중에는 쓰지 않고, 재개하면 그때 되돌린다. 롤백 뒤 관찰 전용(`s2_rollback`)·종료 중에도 쓰지 않는다. 롤백 뒤 관찰 전용은 재개로 풀리지 않는다(기존 규칙). 종료 때 되돌리기를 다시 시도한다. 사용자 모드 선택은 원래 모드로 반영되지만 `s2_rollback` 차단은 남아 5G 우선이어도 OBSERVE다(자동 제어로 돌아오려면 재시작).
    - 되돌리기는 예산 가드를 받지 않지만 전환 기록에 들어가 LTE로 내리는 쪽 예산에 반영된다.
    - `nrctl report` 시뮬레이션에도 같은 규칙(쉬는 중 Wi-Fi → 되돌림 + WATCH)을 넣었다.

18. **같은 값 재선택 감지**(기기 시험에서 발견·수정, 2026-09-28 — **§5.12로 대체됨**: 설정 키를 쓰지 않게 되어 사용자 선택은 키 변화로 가린다. 아래 추정 규칙과 `UserChoice`는 없앴다): USER 알림이 왔는데 지금 값이 컨트롤러가 알고 있는 값과 같을 때, (a) 그 값이 원래 모드와 다르고(컨트롤러가 걸어 둔 값) (b) 알림을 받기 시작한 시각이 이번 실행의 마지막 자기 USER 쓰기가 끝난 지 `SELF_NOTIFY_MS`(10초) 이상 지났으면(또는 이번 실행에 자기 쓰기가 없으면) 사용자가 그 값을 고른 것으로 채택한다(`external_user_change how=reselected` → 사용자 모드 선택, §5.6.6 2번). 규칙은 `UserChoice.reselected`(안드로이드 의존 없음, `UserChoiceTest`).
    - 근거: 자기 쓰기 알림은 쓰기 끝 0.002~0.32초 안에 왔다(7건). 사용자의 누름 알림은 47초 뒤였다. 알림은 작업 스레드에서 처리되므로 쓰기 도중 온 자기 알림도 쓰기 뒤에 처리된다.
    - 시각은 `Observer.onAllowed`가 알림 처리를 시작한 순간이다(그 뒤의 USER 조회가 늦어져도 자기 알림이 늦은 알림으로 보이지 않게 — 검증 재현: 조회 6초 지연 → 오판). 작업 스레드의 앞선 작업만큼 처리가 늦을 수 있어 여유를 10초로 잡았다. 컨트롤러 쓰기 뒤 10초 안의 사용자 재선택은 놓친다.
    - 사용자 선택은 밀린 예약보다 먼저 적용한다(`Policy.userSelected`: 적용 → 새 상태의 예약 처리). 예약을 먼저 돌리면 쉬는 시간이 끝난 재시험이 사용자가 방금 고른 LTE 위에 5G를 쓸 수 있었다(검증 재현). 값이 바뀐 일반 사용자 선택에도 같은 순서가 적용된다.
    - 알림에서만 판단한다. 주기 확인은 같은 값을 구분할 수 없다.
    - 적용 범위: 설정 화면이 예전 값을 보이는 채 사용자가 LTE를 고른 경우만(삼성이 실제로 쓸 때만 알림이 온다). 화면이 이미 LTE로 보일 때의 재선택은 알림이 없어 감지 불가(§5.6.6 2번).
    - 위험: 사용자 조작이 아닌 같은 값 재적용(삼성 자체 등)이 10초 뒤에 오면 원래 5G 사용자를 LTE로 채택한다. 실사용 12시간·기기 시험 기록에서 설명되지 않는 USER 알림은 없었다. 채택은 기록(`reselected`)으로 남으므로 실사용 기록으로 감시한다.

### 5.12 사용자 설계 변경: 설정 = 사용자 고정값 (2026-09-28 제안·결정, 같은 날 구현 — 기기 확인 전)

**기기 확인 결과(2026-09-29, research §2.13) — 전제 불성립.** 쉬는 동안 설정 키는 26(5G 우선) 그대로였다. 그런데도 네트워크 모드 화면은 "LTE 우선"으로 보였다. 삼성 설정 화면은 설정 키가 아니라 **USER 사유 허용 타입**(`getAllowedNetworkTypes(0)`)을 보여 주기 때문이다(삼성 코드 확인).
- 그래서 USER만 바꾸는 이 방식으로는 "설정 화면 = 사용자가 고른 값 그대로"가 되지 않는다.
- 쉬는 중 화면이 이미 LTE로 보이므로, 사용자가 LTE 우선을 눌러도 아무 일도 일어나지 않는다. 치명 결함이 모양만 바꿔 남는다.
- 대안(유력): USER는 사용자 값 그대로 두고 **USER 외 사유(POWER 등)로 NR을 막는다.** 설정 화면은 USER만 보여 주므로 5G 우선 그대로이고, 실제 허용 타입은 모든 사유의 교집합이라 LTE가 된다. 사용자가 LTE 우선을 누르면 USER 값이 실제로 바뀌므로 확실히 감지된다.
  - 기기 확인 필요: ① 셸 권한으로 그 사유를 쓸 수 있는지(같은 값 쓰기로 먼저 확인) ② 설정 화면·상단바가 기대대로 보이는지 ③ 재부팅 뒤 그 사유 값이 남는지. 남으면 데몬이 없을 때 설정 화면으로 풀 수 없는 차단이 되므로 안전장치가 필요하다 ④ 삼성 절전 기능 등이 같은 사유를 쓰는지
  - **기기 실험 결과(2026-09-29, research §2.14):** ① 된다 ② 된다(상단바 LTE, 설정 화면 5G 우선, 그 상태의 LTE 누름을 즉시 감지) ③ **남는다**(재부팅 뒤에도 POWER가 NR 없음) ④ 미확인.
  - ③ 때문에 안전장치가 필요하다. 후보: 데몬이 켜질 때마다 자기가 건 POWER 제한을 먼저 푼다. `nrctl restore`·`doctor`도 POWER를 확인·해제한다. 배포 앱(방법 A)이 부팅 뒤 자동으로 데몬을 켜서 풀게 한다. 동반 앱이 부팅 때 "5G가 막혀 있을 수 있음" 알림을 띄운다(데몬이 공용 저장소에 표시 파일을 남기는 방식).
  - 방향 결정은 사용자 몫이다.
- 아래 구현(USER만 쓰기 + 설정 키로 사용자 선택 판단)은 설치돼 동작한다. 첫 실제 쉬기(09-28 23:56)와 재시험 통과 2번을 확인했다. 설정 화면이 실제를 따라 보이는 점은 예전 S2 방식과 같다.

**구현 상태(2026-09-28 밤).** 사용자가 구현을 결정했다(결정 장부 c211981ddc186884 → now).
- `Actuator`: USER만 쓴다. 설정 키 쓰기와 롤백을 없앴다. USER 쓰기 명령 바로 앞에서 통화 가드와 설정 키 재확인을 한다(보호 규칙 1). 키를 못 읽으면 쓰지 않는다(BLOCKED).
- `UserMode`(새 파일): 키↔USER 짝짓기와 시작 판단(키 우선)을 맡는다. `UserModeTest`로 시험한다.
- `Controller`: 사용자 선택은 설정 키로 판단한다(USER 알림·키 변경 감시 `KeyWatch`·키 재확인 창 끝·통화 끝·30초 주기 확인). 예전 추정 규칙 `UserChoice`와 표시 불일치 점검을 없앴다. `keep-lte` 명령은 쓰지 않는다(설정에서 LTE 우선을 고른다).
  - 사용자 선택 맞춤(`align_*`, 통화 가드만): 맞출 목표를 기억해 두지 않는다. 판단할 때마다 키와 USER를 폰에서 새로 읽고, 사용자 선택이 5G를 포함하지 않는데 USER에 NR이 있으면 뺀다. 그래서 통화로 막혔던 맞춤이 뒤의 새 선택을 덮는 일이 없다.
  - 키 변경은 USER를 읽은 뒤에만 처리 완료로 기록한다. USER를 못 읽으면 다음 확인에서 다시 본다. 그동안의 5G 쓰기는 Actuator의 키 확인(예전 키를 기대)이 막는다.
  - 확인 창에 막힌 재시험은 창이 끝나는 시각에 다시 한다(쓰기 결과에 다시 쓸 시각을 담아 엔진에 넘김).
  - 확인 창 안(USER 알림 직후)에는 맞춤을 하지 않는다. 키가 아직 예전 값일 수 있어서다(예: LTE → 5G 선택에서 USER는 5G, 키는 아직 LTE). 창 끝에 다시 판단한다.
  - 키 변경을 채택할 때 실제 USER의 NR 여부도 엔진에 넘긴다(`userSelected(t, nr, actualNr)`). 사용자 선택은 5G인데 실제가 LTE면 엔진은 쉬는 중으로 보고 조건이 되면 곧바로 재시험한다.
  - 맞춤 명령이 실행됐는데 실패(FAILED)하면 같은 키·USER 상태에서는 다시 쓰지 않는다(`align_failed_hold`, 자동 재시도 없음 §5.6.3). 이 실패 기억은 그 상태가 이어지는 동안만 유효하다: 새 키를 채택하거나 다른 (키, USER) 상태를 한 번이라도 보면 지운다(외부 검증 지적: 예전 실패가 뒤의 새 LTE 선택까지 막았다). 통화로 막힌 것(BLOCKED, 쓰지 않음)은 다음 확인에서 다시 판단한다.
  - 종료 확인에서 키·USER 읽기가 실패하면 5초 간격으로 최대 12번(약 1분) 다시 확인한 뒤에야 비정상 종료로 끝낸다(`stop_deferred why=read_failed`).
  - 종료는 매번 확인 창(3초)을 거친다. 맞춤이 통화 등으로 막히면 끝내지 않고 5초마다 다시 확인한다(`stop_deferred why=align_blocked`). 종료 중 중복 요청은 무시한다.
  - 남는 위험: 삼성의 키 기록이 확인 창(3초)보다 늦으면 종료가 먼저 끝날 수 있다. 이때는 `nrctl stop`이 종료 뒤 설정과 실제를 대조해 알리고, `restore`나 다음 시작이 맞춘다. 3초는 기기에서 틈을 잰 뒤 조정한다.
- `Actuator`의 쓰기 순서: 선기록 → 설정 키 재확인 → 통화 가드(명령 바로 앞) → USER 쓰기.
- `nrctl`: `restore`는 실제 허용 모드를 설정 화면(사용자 선택)에 맞추고 설정 값은 쓰지 않는다. 확인 질문 뒤 쓰기 직전에 다시 읽어, 그 사이 바뀌었으면 쓰지 않는다. `stop` 뒤 설정과 실제를 대조해 어긋나면 알린다. `report`는 새 쓰기 기록(`w_*`)과 맞춤 쓰기를 따로 센다.

**제안(사용자).** 지금 방식(S2: 컨트롤러가 USER 허용 타입과 삼성 설정 키를 함께 바꿈)에서는 쉬는 중(LTE) 사용자가 LTE 우선을 골라도 컨트롤러가 구분하지 못한다. 그래서 재시험이 5G로 되돌린다 → 치명적 결함(§5.11 결정 18, research §2.12). 네트워크 설정에서 사용자가 고른 5G 우선/LTE 우선은 **무조건 고정값**으로 한다.
1. 5G 우선 → 점 표시, 5G 동작. 컨트롤러가 LTE로 쉬게 해도 점은 유지하고, 상단바 표시와 실제 통신은 LTE다. 재시험으로 5G 복귀. 점은 5G 우선인 동안 계속 뜬다.
2. LTE 우선 → 컨트롤러 전부 정지, 즉시 순정 LTE.
3. Wi-Fi 접속 → 순정과 같게. 접속 전 5G 우선이었으면 점이 사라진다(쉬는 중이었으면 원래 모드로 되돌림). 접속 전 LTE 우선이었으면 원래 점이 없다.

| 쉬는 중 LTE 선택을 가릴 수 있다 | 5G 우선인 동안 키는 늘 26이라 설정 화면에 5G 우선이 보인다. 그래서 LTE 우선 누름은 삼성 화면 입장에서 "변경"이다. 화면에 다른 값이 보일 때 누르면 삼성이 쓰고 알림이 왔고(09-28 20:24:49), 이미 보이는 값을 누르면 아무 일도 없었다(20:54~56). 컨트롤러가 키를 쓰지 않으므로 키 26→9 변화는 사용자(또는 사용자 루틴)만 만든다 | 새 조합(키 26·USER LTE에서 누름 → 키 9)은 **미시험**. 삼성은 USER 변경 완료 뒤 키를 기록한다(§2.6 분석) → USER 알림 시점에 키가 이미 바뀌었다고 가정하지 않는다 |
| 지금의 10초 추정 규칙이 필요 없어진다 | 키 변화는 컨트롤러 자신의 쓰기와 섞이지 않는다. 현재 설치본의 규칙(`UserChoice`)은 작업 큐 지연(예: 주기 점검의 설정 조회가 10초 넘게 걸림)이 겹치면 자기 알림을 사용자 선택으로 오인할 수 있다(외부 검증 재현) | 새 방식 구현 때 제거 |
| 켤 때 원래 설정 판단 | **설정 키를 사용자의 고정값으로 반영한다(구현: `UserMode.decide`).** 예전 `Saved.decide`는 USER 값과 상태 파일만 봐서 "컨트롤러가 남긴 LTE(키 26)"와 "데몬이 없는 사이 사용자가 LTE를 고름(키 9)"을 구분하지 못했다(외부 검증 지적). 구현한 규칙: 원래 모드 = 키가 가리키는 모드. 키 26·USER LTE면 원래 5G이고 조건이 되면 재시험한다. 키 9·USER 5G면 원래 LTE이고 시작 때 LTE로 맞춘다. 상태 파일 흔적은 판단에 쓰지 않고, 사용자에게 묻지도 않는다(설정 화면이 곧 사용자 답이다) | 구현됨(PC 시험) |
| 재부팅 위험 | 재부팅 시 USER 허용 타입이 적용되고 삼성 저장 모드는 재적용되지 않았다(research §2.5②, 키 9·USER 840583 1회). 반대 조합(키 26·USER LTE)도 같다고 **추정**한다. 그러면 쉬는 중 재부팅되면 "설정 5G 우선, 실제 LTE, 점 없음"으로 남는다. PC로 켜면 위 새 규칙이 키 쪽으로 맞춘다. 자동 재기동(로드맵 A)이 생기면 사라지는 위험이다 | 추정(반대 조합 재부팅 미시험) |

| 삼성 자동 재적용 | 확인한 기록(5일 치 삼성 이력 §2.3, 12시간 실사용, 기기 시험)에서 의도하지 않은 재적용은 발견하지 못했다. 다만 각 삼성 경로 호출의 주체(사람/루틴)는 사용자 보고에 기댄다. 쉬는 중에 키 26·USER LTE를 오래 유지하는 조합은 지금까지 쓰지 않았다(S2가 키도 9로 내렸다) | 새 조합의 장시간 동작 미확인 |
| Wi-Fi(요구 3) | 보류·점 숨김·복귀는 기기 확인(research §2.12). 쉬는 중 Wi-Fi 되돌리기는 PC 시험만 통과(기기 기록에 `wifi_restore` 0건). 새 방식에서는 되돌리기가 USER 쓰기만 하면 된다 | 복원 쓰기 기기 미확인 |

**바뀌는 범위(구현 시).**
- `Actuator`: S2(설정 키 쓰기·롤백)를 빼고 USER 쓰기만 남긴다. 롤백 관련 상태(`s2_rollback` 등)도 줄어든다.
- `Controller`: 사용자 선택을 설정 키로 판단한다. USER 알림 뒤 키를 다시 읽고(삼성이 키를 나중에 쓰므로 짧은 지연 뒤 한 번 더), 30초 주기 확인에서도 읽는다. 필요하면 설정 변경 감시를 붙인다. `UserChoice`는 제거한다.
- **5G를 켜는 쓰기의 보호 규칙**(외부 검증 지적: 키 재확인을 기다리는 사이 재시험이 사용자 LTE 선택을 덮을 수 있음). 삼성은 USER 변경을 끝낸 뒤 키를 쓰므로 다음 세 규칙을 함께 둔다.
  1. **쓰기 직전 키 확인**: 5G를 켜는 모든 쓰기(재시험·Wi-Fi 되돌리기·종료 되돌리기·재개)는 USER 쓰기 바로 앞에서 키를 다시 읽는다. 키가 가리키는 모드가 5G 우선이 아니면 쓰지 않고, 그 모드를 사용자 선택으로 채택한다.
  2. **확인 대기 중 보류**: 자기 쓰기로 설명되지 않는 USER 알림이 오면, 짧은 지연 재확인이 끝날 때까지 5G를 켜는 쓰기를 미룬다(통화 가드처럼 막힘 처리 후 재확인 시각에 다시 판단).
  3. **경합 뒤 사용자 쪽으로 맞춤**: 그래도 경합으로 컨트롤러가 5G를 쓴 직후 키가 LTE 계열로 바뀐 것이 감지되면, 그 모드를 사용자 선택으로 채택하고 USER를 사용자 선택 값으로 되돌린다. 사용자 선택을 따르는 쓰기이므로 통화 가드만 받는다. 설정 키는 여전히 쓰지 않는다.
  4. **종료 전 확인 창**(외부 검증 지적: 종료 되돌리기 뒤 데몬이 먼저 끝나면 늦게 기록된 LTE 키를 아무도 정리하지 못함): 종료 되돌리기로 5G를 쓴 뒤 바로 끝내지 않는다. 확인 창(USER 알림~키 기록 틈 실측값 + 여유) 동안 키를 다시 읽는다. 키가 LTE 계열로 바뀌었으면 3번처럼 USER를 사용자 선택 값으로 맞춘 뒤 끝낸다. PC `nrctl stop`도 데몬 종료 뒤 키와 USER를 한 번 더 대조해 어긋나면 알린다. 다음 시작의 키 우선 판단(`UserMode.decide`)이 마지막 안전망이다: 키 LTE·USER 5G면 흔적 여부와 관계없이 키 쪽(LTE)으로 맞춘다.
  - 이 넷으로 "LTE 우선 선택 → 정지"는 누름부터 키 기록까지의 짧은 틈에서도, 그 사이 종료가 겹쳐도 결국 사용자 선택으로 수렴한다. 틈에서 5G가 한 번 잠깐 켜질 수 있는 경우는 3번(실행 중)이나 4번(종료 중)이 곧바로 되돌린다(기기에서 틈 길이 확인 — 기기 확인 1).
- 시작 검사: "S2 가능"을 "설정 키 읽기 가능"으로 바꾼다.
- 시작 판단: `Saved.decide`를 없애고 `UserMode.decide`(키 우선, 상태 파일 미사용)로 바꿨다.
- `Policy`: 상태기계는 그대로다. INACTIVE/WATCH 판단 입력이 키 기반 모드로 바뀐다.
- 문서: P5를 교체하고, §5.6.5·§5.11(결정 18·19)을 대체 표시한다.

**기기 확인(구현 뒤, 사용자 승인).**
1. 쉬는 중(키 26·USER LTE) 사용자가 LTE 우선을 누르면 키가 9로 바뀌는지, USER 알림과 키 기록 사이의 틈이 얼마인지(보호 규칙 2의 대기 시간 근거).
2. 같은 상태에서 상단바가 LTE/LTE+로 보이는지(사용자 육안).
3. 쉬는 중 Wi-Fi 연결 → 원래 모드(5G 우선) 되돌림과 점 숨김.

### 5.13 통신사 권한 경로: 재부팅 뒤에도 PC 없이 도는 구조 (2026-09-29 PoC, 제품 구조 후보)

**왜 필요한가.** §5.12의 POWER 방식은 원하는 모습(쉬는 동안 설정 화면은 5G 우선, 상단바는 LTE)을 낸다. 그러나 허용 타입을 바꾸려면 `MODIFY_PHONE_STATE`(signature|privileged) 또는 carrier privilege가 필요하다.
- 지금은 셸(ADB) 권한으로 띄운 데몬이 이 일을 한다. 셸 프로세스는 재부팅 때 죽고, 루트 없이는 폰 스스로 셸 권한을 되살릴 수 없다.
- 무선 디버깅은 신뢰한 Wi-Fi 접속이 필요하다. 폰 핫스팟만 켠 상태에서는 쓸 수 없다.
- 일반 앱이 받을 수 있는 경로는 carrier privilege 하나다.

**방법(정확한 표현).** Android CarrierConfig에 앱 서명 인증서를 테스트용 override로 추가해 Telephony가 carrier privilege를 인정하게 한다. SIM은 건드리지 않는다.
- PC 설치 프로그램이 한 번 한다(shell 권한): 지금 인증서 목록(`carrier_certificate_string_array`)을 읽고, 앱 인증서를 **덧붙인** 목록을 영구(persistent) override로 저장한다.
- 기존 항목은 덮어쓰지 않는다. 제거할 때는 원래 상태로 정확히 되돌린다.
- 유지 범위는 **"재부팅 후 유지"**다. 풀릴 수 있는 경우: SIM·eSIM 교체, 공장 초기화, 전화(Telephony) 앱 데이터 삭제, 삼성 OTA 등으로 통신사 설정 패키지 버전이 바뀜(코드상 버전이 다르면 저장분을 버림), Android 버전 변경.

**PoC 결과(research §2.15).**

| 관문 | 내용 | 결과 |
|---|---|---|
| 1 | override 뒤 앱의 `hasCarrierPrivileges()` | 통과 |
| 2 | ADB가 아니라 앱 프로세스가 `setAllowedNetworkTypesForReason(CARRIER, …)`로 NR 제거·복원 | 통과(양방향). LTE 묶음 유지. 호출 계기는 PC 시험 명령이었고, 쓰기는 앱이 자기 권한으로 했다 |
| 3 | 재부팅 뒤 ADB 명령 없이 권한 유지(결정적 관문) | 통과. 앱이 부팅 알림과 통신사 설정 알림을 받아 스스로 확인 |
| 4 | 부팅 자동 실행과 장시간 생존 | 부팅 자동 실행은 통과. 장시간 생존은 계측 중(22:53~) |
| 5 | 앱 프로세스에서 판단 재료 수신 | 7/9 등록과 첫 사건 수신. 허용 타입 알림은 설정 키 감시와 사유 값 읽기로, nrState는 PCC로 대체. 계속 수신되는지는 콜백 보관판(22:53~)으로 계측 중 |

**제품 구조안(사용자 결정 전).**
- **폰 앱 하나.** 상주 서비스(전면 서비스)가 지금 데몬의 판단 엔진(`Policy`)을 그대로 돌린다. 동반 앱의 점도 이 앱이 띄운다.
- **쉬기 = CARRIER 사유에서 NR만 뺀다.** USER 사유와 설정 키는 절대 쓰지 않는다.
  - 설정 화면은 USER만 보여 주므로 5G 우선 그대로이고, 상단바와 실제 연결은 LTE다.
  - 막는 값은 "지금 CARRIER 값에서 NR 비트만 뺀 것"으로 한다. 기기별 고정값을 쓰지 않는다.
- **사용자 선택 = USER 사유(설정 화면 값).** 컨트롤러가 USER를 쓰지 않으므로 USER 변화는 곧 사용자(또는 사용자 루틴)의 선택이다.
  - 감지: 설정 키 변경 감시(앱에서 됨)를 신호로 삼고, 그때 사유 값을 다시 읽는다. 주기 확인을 보조로 둔다.
  - §5.12의 보호 규칙 1~4(키 재확인·확인 창·경합 뒤 맞춤·종료 확인 창)는 "컨트롤러가 USER를 쓴다"는 전제에서 나온 것이다. 이 구조에서는 대부분 필요 없어진다. 구현 때 하나씩 재검토한다.
- **PC 설치 프로그램(한 번):** 앱 설치 → 인증서 덧붙임(영구) → 배터리 최적화 제외 → 첫 시작. 제거 명령도 같이 둔다.
- **남는 한계:** 설치에 PC가 한 번 필요하다. 위 "풀릴 수 있는 경우"가 생기면 PC로 다시 설치해야 한다.

**안전 규칙(구조안에 포함).**
1. **설치 전 기록.** 기존 인증서 목록과 기존 override를 임시·영구 층별로 PC와 폰에 기록한다. `null` override는 그 폰의 임시 override를 전부 지우고, `persistent=true`일 때만 영구 override와 파일도 전부 지운다. 영구로 넘긴 묶음은 임시 층에도 먼저 합쳐지고(추출본 908행), 재적용은 교체가 아니라 합치기(`putAll`)다. 그래서 제거는 "두 층 모두 지우기(`null, true`) → 설치 전 영구 override 재적용(영구) → 임시 층만 다시 지우기(`null, false`) → 설치 전 임시 override 재적용(임시)" 순서로 한다. 레퍼런스 기기는 설치 전 override가 없었으므로 `null, true` 한 번이면 된다. 층별 값을 dumpsys 글자로만 읽을 수 있어 값 형식(정수·문자열 배열 등)을 되살리는 방법은 구현 때 정한다.
2. **제거 때 정확 복원.** CARRIER 사유를 설치 전 값으로 shell이 되돌린다. 앱의 공개 API는 LTE_CA 비트를 뺀 값만 쓸 수 있기 때문이다. 이어서 override 복원, 배터리 최적화 제외 해제, 앱 삭제 순으로 한다.
3. **꺼지기 전 풀기.** 종료 방송(`ACTION_SHUTDOWN`)을 받으면 쉬는 중 제한을 푼다. 부팅 때 CARRIER에 NR이 없고 쉴 이유가 없으면 즉시 푼다.
4. **권한을 잃었을 때 — 남는 위험(시간 상한 없음).** 제한 값은 폰 저장소에 남고 만료 시각이 없다(AOSP는 사유별 값만 저장). 앱이 권한을 잃으면 이미 건 제한을 풀 수 없다.
   - 원칙: 쉬는 중 건 제한은 **해제 동작이 실행되지 않거나 성공하지 못하는 동안 계속 남는다.** 쉬기 5분 단위는 앱이 살아 있을 때만 의미가 있다.
   - 권한이 남아 있어도 남는 경로: 쉬는 중 사용자가 앱을 강제 중지함(강제 중지된 앱은 사용자가 다시 열 때까지 부팅 알림도 받지 못한다는 안드로이드 규칙 — 이 기기 미확인) → 앱을 열거나 PC로 복구할 때까지. 쉬는 중 사용자가 앱을 삭제함 → 삭제는 제한을 풀지 않으므로 PC로 복구할 때까지. 앱이 죽었다 스스로 다시 뜨는 경우(상주 서비스 재시작)는 다시 뜰 때 제한을 확인해 푼다(구현 필요).
   - 권한까지 잃는 경로: 쉬는 중에 종료 방송 없이 꺼짐 → 다음 부팅에서 override가 풀림(OTA로 통신사 설정 패키지 버전이 바뀜, SIM 교체 등) → 앱을 다시 열어도 풀 수 없고 PC로만 복구된다.
   - 정상 경로에서는 막힌다: 보통 재부팅과 OTA 재부팅은 종료 방송을 보내므로 규칙 3이 먼저 푼다. 권한이 남은 채 부팅하면 앱이 곧바로 푼다.
   - 앱이 할 수 있는 것: 권한 상실을 감지하면 사용자에게 "PC 연결 필요"를 알린다. PC는 shell로 정확히 복원할 수 있다.
   - 확인할 것: CARRIER 값이 이 기기에서 재부팅 뒤 실제로 남는지(POWER는 남았다), 사용자 스스로 푸는 길 후보인 모바일 네트워크 설정 초기화가 삼성에서 USER 외 사유를 지우는지(AOSP는 지운다, research §4).
   - 이 위험을 받아들일지는 제품 착수 때 사용자와 정한다.
5. **다른 주체와의 충돌.** 통신사 앱이나 삼성 기능이 CARRIER 사유를 쓰면 서로 덮어쓸 수 있다. 앱은 자기가 쓴 값과 다르면 쓰지 않고 기록만 한다(외부 제한은 `HOLD`, §5.6.6과 같다).

**확인 남은 것.** 관문 4 장시간 생존, CARRIER 값의 재부팅 뒤 유지 여부, CARRIER로 막은 상태의 설정 화면 육안 확인, 권한 상실 시 복구 경로(삼성의 네트워크 설정 초기화).

**제품 앱의 보안 조건.** 통신사 권한을 가진 앱이므로 다른 앱이 부를 수 있는 입구(방송 수신기·서비스·콘텐츠 제공자)를 열어 두지 않는다. 시험 명령이 필요하면 발신자에게 DUMP 권한을 요구하고(`android:permission=DUMP`: shell은 가지고 있고 일반 앱은 없다. 다만 개발용 권한이라 PC가 `pm grant`로 준 앱은 가질 수 있다) USER 사유는 받지 않는다(PoC 22:53판과 같다).

| 단계 | 내용 | 완료 기준 |

| **Phase 4** 확장 | 다른 기기(삼성 One UI 6+, Pixel, Xiaomi), 백엔드 C, 무선 디버깅 자동 재기동(Wi-Fi 필요) 검토 | 기기별 probe 보고서 |

**Phase 0 잔여 상태** (research §2.4·§2.5)
1. `setsid` 데몬 생존 — **통과**. 약 18.8시간·반복 깊은 잠 누적 약 7.1시간 동안 유지(케이블 분리는 사용자 보고). adbd 재시작 시 종료 여부는 미시험.
2. 재부팅 후 유지 — **해결**. 설정 화면 경로는 유지 확인. 컨트롤러 방식(`cmd phone`만 변경)도 역방향 재시험에서 재부팅 시 USER 허용 타입(DB)이 적용되고 삼성 저장 모드는 재적용되지 않음을 확인(1차 시도는 루틴·수동 조작 개입으로 무효).
3. 설정 경로 재적용 — 선택한 값의 USER 반영 확인(적용 지연 미측정). 어긋난 상태에서 저장값과 같은 모드를 삼성 경로로 다시 적용해도 반영됨(삼성 기록, 주체는 사용자 루틴, 화면 미확인).
4. binder — 단발 조회로 nrState 원값 확인. **이벤트 구독 확인**(2026-09-28, §5.3 Phase 1 구현): 물리채널 등 여섯 종류의 첫 알림 수신, 허용 타입 알림 등록 성공. 허용 타입 **변경** 알림도 수신 확인(2026-09-28, 사용자의 5G 우선·LTE 우선 선택 모두 즉시 도착).
5. 사유별 초기값 — 사유별 조회는 미설정 사유와 구분 불가(네 사유 모두 같은 값) 확인. 허용 타입 알림은 **등록 시 현재값을 보내지 않았다**(7회 기동) → 초기값은 USER 직접 조회, 이후 변경은 알림으로 받는다. USER 외 사유의 초기 상태는 여전히 알 수 없다(§5.6.6 3번 규칙은 변경 알림 기반).
6. **삼성 표시 동기화 경로(백엔드 S)** — **레퍼런스 기기에서 확보**(2026-09-27).
   - 앱 내부 분석(읽기 전용): 삼성 통로 네 곳은 모두 삼성·시스템 앱 전용이었다. 삼성 내부 동작이 "USER 허용 타입 변경 + 설정 키 기록"임을 확인했다(research §2.6).
   - 사용자 승인 후 S2(`cmd phone` + `settings put global`)로 5G↔LTE를 시험했다. 설정 화면이 양방향으로 따라오는 것을 사용자가 눈으로 확인했다(research §2.8).
   - 남은 확인 ❓: 시스템 프레임워크 부작용, 다른 기기, 같은 값 재선택 관측 수단(§5.6.6).
7. **상단바 작동 표시** — 시험 완료(2026-09-27). 새 이름의 자리는 삼성 상단바에 안 그려지고, 빈 SIM2 VoLTE 자리는 신호 막대 바로 옆에 그려진다. 색은 한 가지로 칠해진다(research §2.7). 남는 점 위험은 §5.8에 적었다.

개발 환경(2026-09-26 설치 완료, research §2.4): Temurin JDK 17.0.20.1, Android SDK(build-tools 37.0.0, platforms android-33·36, platform-tools 37.0.1, cmdline-tools 23.0), Gradle 9.8.0. 사용자 환경변수 `JAVA_HOME`·`ANDROID_HOME` 등록. 도구체인은 `phase0/probe`(javac → d8 → 폰 app_process)로 끝까지 동작 확인했다.

## 9. 측정·검증 계획 (A/B)

사용자의 원래 문제의식(변인 통제 없는 배터리 비교 비판)을 이 도구 평가에도 똑같이 적용한다.

- **조건**: 같은 경로·요일·시간대. 컨트롤러 ON / OFF(5G 기본 모드) / LTE 고정(현재 습관) 세 조건을 번갈아 측정한다. **케이블 분리 상태**(USB 연결은 충전이 섞임).
- **수집**: `charge_counter` 변화량, 화면 켜짐 시간, 셀룰러 송수신 바이트, 데이터 사용 중 NR 연결/끊김 횟수, 전환 횟수와 추정 단절 시간(`dumpsys batterystats` 포함, 측정 전 `--reset`).
- **정규화**: 배터리 변화량을 화면시간·데이터량 기준으로 함께 보고한다(동일 작업량 비교).
- **해석 한계**: 한 사람·한 기기·한 경로의 결과이므로 일반화하지 않는다. 결과는 "이 환경에서의 순이득"으로만 표현한다.

## 부록 A. 비트마스크

- 비트 위치 = `NETWORK_TYPE_* − 1`. NR(20) → bit 19, LTE(13) → bit 12, LTE_CA(19) → bit 18.
- 20자리 이진 문자열의 **맨 왼쪽이 NR**.

| 마스크 | 값 | 비고 |
|---|---|---|
| `01001101001110000111` | 316295 | 레퍼런스 기기 현재값(삼성 모드 9: LTE/3G/2G) |
| `11001101001110000111` | 840583 | 위 + NR(삼성 모드 26) |
| `10000000000000000000` | NR only | **사용 금지** 🔒 |

## 부록 B. 명령 레퍼런스 (레퍼런스 기기에서 확인)

```bash
adb shell cmd phone get-allowed-network-types-for-users -s 0
adb shell cmd phone set-allowed-network-types-for-users -s 0 <20비트 이진>   # 출력 'completed' 확인 필수
adb shell dumpsys telephony.registry        # 관측(nrState 마스킹)

```

## 부록 C. 용어
- **NSA / EN-DC**: LTE를 앵커로 NR을 보조셀(SCG)로 붙이는 5G 방식.
- **SA**: LTE 앵커 없이 NR 단독 접속.
- **PCC**: Physical Channel Config. 현재 연결된 주/보조 셀 목록.
- **active-drop**: 데이터 사용 중 NR 보조 연결이 끊긴 사건(본 설계 정의).
- **쿨다운**: NR 비허용을 유지하는 시간.
- **재시험(probe)**: 쿨다운 후 NR을 다시 허용하고 평가하는 창.
